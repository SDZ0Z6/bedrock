# Bedrock 成本监控平台

用 Python + Flask 搭的轻量看板。把 `cred.xlsx` 里的账号台账、AWS Cost Explorer 的
实际消费、CloudWatch 的调用量拼在一起：既能看每个账号的额度使用情况、全部账号的
收入和毛利，也能进到某一个账号，看它按服务/标签的成本明细、各模型的调用与 token
走势、配额和预估花费。

## 快速开始

最省事的方式是双击 `run.bat`（它自己设好 `PYTHONPATH`，不用装包）。

想按标准方式来：

```bash
python -m pip install -e ".[dev]"
```

然后启动：

```bash
python -m bedrock_cost
```

浏览器打开 <http://127.0.0.1:5000>，用 `.env` 里的 `AUTH_USERNAME` / `AUTH_PASSWORD` 登录。

> 装包时会生成一个 `bedrock-cost` 命令，但 Windows 应用商店版 Python 的用户级
> `Scripts` 目录默认不在 PATH 上，所以直接敲 `bedrock-cost` 可能找不到。
> `python -m bedrock_cost` 在哪种装法下都能用，推荐用它。

左侧导航有三个入口：

| 页面 | 路径 | 数据源 | 用途 |
|---|---|---|---|
| 概览 | `/` | Cost Explorer + CloudWatch | 账号卡片墙：每个账号的额度 / 累计消费 / 使用率 / 余额（自启用日期算起）、用量状态（活跃 / 已中断）、生命周期；上面三张图：额度使用、近 30 天成本、消费构成 |
| 账号 | `/account/<号码>/` | 各自不同 | 某一个账号的六个页签：摘要、成本、用量、预估、时间线、配额。点概览卡片右上角的「查看详情」进来；从侧边栏进来是上次看的那个账号 |
| 账号管理 | `/accounts/` | 本地台账 | 台账的增 / 改 / 停用 / 删除、告警开关、生命周期标签、头像 |

还有一个**运营看板**（`/ops/`：收入、AWS 原价、毛利，需要关注的账号和最近的告警，全部账号的
模型与区域用量），**先下线了**：默认不注册这个页面、侧边栏也没有入口；`.env` 里设
`OPS_DASHBOARD=1` 就回来，见《运营看板》一节。

老网址 `/cost-usage`、`/model-usage`、`/model-quota`、`/cost-estimate` 还能用：跳到
「上次看的那个账号」对应的页签，查询参数原样带过去（`account=号码#行号` 也认）。

查询页一次只看一个账号，没有「全部账号」：选过的账号记在会话里，各页签共用。账号到处
都是「头像 + 邮箱 + 号码」一起出现，**邮箱是主行、号码是副行**——号码一眼认不出是谁，邮箱
在台账的 `EMAIL` 列。没填邮箱的账号号码当主行。

侧边栏可以点左上角的箭头收起成一条图标轨（60px）。收起后几个入口都只剩图标，
尺寸完全一致，悬浮可以看到 `title` 里的名字。
收起状态存在 `localStorage`，跨页面和重启浏览器都保持；`<head>` 里有一小段内联
脚本在首次绘制前就把状态套上，所以不会出现「先展开再收起」的闪动。窄屏
（≤900px）侧边栏本来就是横条，收起按钮会隐藏。

## AK/SK 需要什么权限

`cred.xlsx` 里每个账号的 AK/SK 只用来**读**，一个写操作都没有。下面这份策略是按
代码里实际发出的 API 调用逐条对出来的，不多不少：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "CostPages",
      "Effect": "Allow",
      "Action": "ce:GetCostAndUsage",
      "Resource": "*"
    },
    {
      "Sid": "ModelUsagePage",
      "Effect": "Allow",
      "Action": [
        "cloudwatch:ListMetrics",
        "cloudwatch:GetMetricData"
      ],
      "Resource": "*"
    },
    {
      "Sid": "ModelIdAndTags",
      "Effect": "Allow",
      "Action": [
        "bedrock:ListInferenceProfiles",
        "bedrock:ListTagsForResource"
      ],
      "Resource": "*"
    },
    {
      "Sid": "QuotaPage",
      "Effect": "Allow",
      "Action": "servicequotas:ListServiceQuotas",
      "Resource": "*"
    }
  ]
}
```

逐条说明：

| 权限 | 谁在用 | 干什么 | 缺了会怎样 |
|---|---|---|---|
| `ce:GetCostAndUsage` | 概览、运营看板、账号页的摘要 / 成本页签 | 拉消费金额，并按标签拆 TAG / UNTAG | 这个账号的消费查不到，右上角报原因；运营看板不算它 |
| `cloudwatch:ListMetrics` | 账号页的用量 / 预估页签、运营看板、概览的用量状态 | 发现该账号近两周用过哪些模型 | 用量为空、状态显示「读不到 CloudWatch」 |
| `cloudwatch:GetMetricData` | 同上 | 拉调用次数和 token 数 | 同上 |
| `bedrock:ListInferenceProfiles` | 用量页签、配额页签 | 把 12 位不透明 ID 解析成可读名字和底层模型；配额页签的表格主键就是它返回的 ARN | 用量页签显示原始 ID；配额页签退回按「模型 × 区域」列，ARN 和模型 ID 两列留空。**不影响配额数字** |
| `bedrock:ListTagsForResource` | 用量页签 | 读推理配置上的 `map-migrated` 标签，判定有标签 / 无标签 | 全部流量被当成「无标签」，页面会明确提示 |
| `servicequotas:ListServiceQuotas` | 配额页签 | 拉 Bedrock 的 token 配额 | 配额页签提示读不到 |

报错会说清楚是**谁拒的**：组织的 SCP（服务控制策略）显式拒绝、凭证本身缺权限、
凭证无效、被限流还是网络问题（`aws_errors.py`）。被 SCP 拒的时候，补 IAM 权限没有用，
得去改组织那边的策略——右上角报错的「查看详情」里有 AWS 原话和策略 ARN。

几点说明：

- **预估页签不需要新权限。** 它用的是用量页签已有的 `cloudwatch:ListMetrics`
  和 `cloudwatch:GetMetricData`；单价来自 AWS 的**公开**价目表端点，不带凭证访问，
  所以**不需要** `pricing:GetProducts`。
- **不需要 `ce:GetTags`。** 早期文档里列过它，那是当初排查标签键时手动用的，
  代码里并不调用。已移除。
- **不需要任何写权限**，也不需要 `bedrock:InvokeModel`——这个平台只读监控数据，
  从不发起模型调用。
- **`Resource` 只能是 `*`**：Cost Explorer、CloudWatch 的 `GetMetricData`、
  Service Quotas 这几个接口都不支持按资源收敛。真正的收敛手段是上面这份
  Action 列表本身。
- **计费**：`ce:GetCostAndUsage` 约 0.01 USD/次，`cloudwatch:GetMetricData` 约
  0.01 USD/1000 个 metric，其余（`ListMetrics`、`ListServiceQuotas`、
  `ListInferenceProfiles`、`ListTagsForResource`）不计费。平台对结果做了缓存，
  见《缓存》一节。
- **想更省事**：AWS 托管策略 `ReadOnlyAccess` 一定够用，但它把整个账号的读权限
  都给了出去。既然这套密钥要放在一台公网服务器上（见 `DEPLOY.md`），
  强烈建议用上面这份最小策略——真泄露时损失的上限就是它框住的。

### 怎么配

1. IAM 控制台 → 策略 → 创建策略 → JSON，贴上面那段，命名如 `BedrockMonitorReadOnly`
2. IAM → 用户 → 创建用户（不需要控制台访问）→ 直接附加上面这条策略
3. 该用户 → 安全凭证 → 创建访问密钥 → 用途选「在 AWS 外部运行的应用程序」
4. 把 AK / SK 填进 `cred.xlsx` 对应账号那一行

每个账号各建一个这样的用户，互不相干。

## 各页面的 API 调用与费用

下面的次数按**台账里 N 个启用账号、4 个美区**给公式。标了「实测」的数字是改版前用
botocore 事件钩子量的（当时 2 个账号、每个账号约 11 个应用推理配置），量级仍然适用；
那时的几个查询页是「全部账号」口径，现在的账号页签一次只查一个账号，次数要再除以账号数。

### 概览 `/`

| 调用 | 次数 | 公式 | 计费 |
|---|---|---|---|
| `ce:GetCostAndUsage` | 2N | 累计消费 N 次 + 近 30 天每天的成本 N 次 | 约 $0.01/次 |
| `cloudwatch:GetMetricData` 等 | 4N | 用量状态：每个账号 4 个区，近 30 天按小时 | 约 $0.01/1000 metric |

一个账号一次请求就同时拿到 TAG 和 UNTAG 两部分（靠 `GroupBy` 标签键，本地归类）。
累计消费冷加载实测 22.6 秒（2 个账号），时间全在 Cost Explorer 自己的响应上。
「近 30 天成本」那张图单独缓存 2 小时，用量状态缓存 5 分钟。

### 运营看板 `/ops/`

| 调用 | 次数 | 公式 | 计费 |
|---|---|---|---|
| `ce:GetCostAndUsage` | N（+ 概览那 N 次累计） | 每个账号一次：近 12 个月的逐日数 | 约 $0.01/次 |
| `cloudwatch:GetMetricData` | 3 × 4N | 调用次数、输入、输出 token 三个指标 × 4 个区，这一段和上一段一次查完 | 约 $0.01/1000 metric |

本月、上月、近 30 天、今年和各自的上一段、近 12 个月的走势，全从那**一份逐日数**里切，
所以切时间段不花 CE 的钱；逐日数缓存 2 小时。额度和用量状态和概览共用缓存。四份数据
并发着拿，哪一份出错只影响它那一块。

### 账号页 · 摘要 `/account/<号码>/`

累计消费 1 次 + 近 30 天每天的成本 1 次 CE，近 7 天调用 4 次 `GetMetricData`；近 7 天有调用的，再按
「预估」页签的算法估今天的花费（token 指标 × 4 个区，同一份缓存）。配额卡**只读缓存**（第一次查配额要
45 秒，不能拖慢摘要），在配额页签查过一次之后才有。

### 账号页 · 成本 `/account/<号码>/cost`

| 调用 | 次数 | 公式 | 计费 |
|---|---|---|---|
| `ce:GetCostAndUsage` | 1 | 每次换维度 / 粒度 / 区间 | 约 $0.01/次 |

服务维度用两级 `GroupBy [SERVICE, TAG]`，所以逐格加权也只要一次请求。
冷加载实测 2.7 秒。

> 换维度、换粒度、换日期区间都会绕开缓存重新请求（缓存键包含这些参数）。
> 反复拖时间范围是这个平台最容易花钱的操作。

### 账号页 · 用量 `/account/<号码>/usage`

| 调用 | 次数 | 公式 | 计费 |
|---|---|---|---|
| `cloudwatch:ListMetrics` | 4 | 区域数 | 免费 |
| `cloudwatch:GetMetricData` | 约 24 | 3 个指标 × 这一段和上一段 × 4 个区（四张指标卡要比上一段） | 按请求的 metric 数计 |
| `bedrock:ListInferenceProfiles` | ≤4 | 有数据的区 | 免费 |
| `bedrock:ListTagsForResource` | 配置数 | 逐个配置读标签 | 免费 |

`GetMetricData` 一次请求里打包了很多 metric，一次页面加载远不到 $0.01。慢的是
`ListTagsForResource`（`list_inference_profiles` 不返回标签，只能逐个读），改版前实测
冷加载 39～59 秒、大头在它；这部分单独缓存 1 小时，切换指标、标签筛选、时间窗口时
不会重新读配置，只重新拉指标。

### 账号页 · 配额 `/account/<号码>/quota`

| 调用 | 次数 | 公式 | 计费 |
|---|---|---|---|
| `servicequotas:ListServiceQuotas` | 约 40 | 每区配额总数 ÷ 每页 100 × 4 个区 | 免费 |
| `bedrock:ListInferenceProfiles` | 4 | 1 × 4 个区 | 免费 |

**不花钱，但冷加载要 40～50 秒。** 慢的原因是 `ListServiceQuotas`
**按账号跨区限流到约 1 请求/秒**：四个区一共约 40 页，串行实测 43.9 秒，
八个请求并发实测 46.3 秒——**并发一点没快**。代码仍然并发发，因为这样四次
`ListInferenceProfiles` 能顺带跑完、不额外占时间。

想绕开这个限流只有 `GetServiceQuota` 点查一条路（QuotaCode 实测跨区完全一致，
35/35 相同），但当前凭证只有 `ListServiceQuotas` 权限，`GetServiceQuota` 被拒，
所以走不通。缓存 6 小时，之后打开是毫秒级。

### 账号页 · 预估 `/account/<号码>/estimate`

| 调用 | 次数 | 公式 | 计费 |
|---|---|---|---|
| `cloudwatch:ListMetrics` | 4 | 区域数 | 不计费 |
| `cloudwatch:GetMetricData` | 4 | 区域数（每次 模型数×4 个 metric） | 约 $0.01/1000 metric |
| AWS 价目表 | 1/天 | 公开 HTTP 端点 | 不计费，**不需要凭证** |

不调用 Cost Explorer，所以看今天花了多少是不花 CE 钱的。

### 客户 `/customers/`、`/customers/<编号>`

| 调用 | 次数 | 公式 | 计费 |
|---|---|---|---|
| `ce:GetCostAndUsage` | M | 客户名下每个启用的账号查一次按天的消费（从启用日期到今天） | 约 $0.01/次 |
| `cloudwatch:GetMetricData` | 4K + 4J | 详情页的「近 24 小时调用」：还在用的 K 个账号（没结算、没停用）× 4 个区；今日预估再按其中 24 小时里有调用的 J 个账号 × 4 个区查 token | 约 $0.01/1000 metric |

列表页查全部客户名下的账号，详情页只查这个客户的，两边共用同一份缓存（15 分钟）。停用的账号
不查：用 `customer-costs.json` 里存下来的历史，一次都没存过的才查一次。

### 账号页 · 时间线 `/account/<号码>/timeline`

| 调用 | 次数 | 公式 | 计费 |
|---|---|---|---|
| `ce:GetCostAndUsage` | 1 | 这个账号按天的消费（从启用日期到今天），算上量、终止、额度预警 | 约 $0.01/次 |

和客户页查的是同一个东西、同一份缓存：刚看过客户页再点进来，不再查。停用的账号同样用存下来的历史。

### 账号管理 `/accounts/`、设置 `/settings/`

不调用任何 AWS API，只读写本地文件（台账、操作日志、登录记录），**不花钱**。

### 缓存之后

**所有页面命中缓存后都是 0 次 API 调用、0 成本、毫秒级返回**（实测 0.00～0.03 秒）。
各自的缓存期见下面《缓存》一节。

### 大致的月度成本

只有 Cost Explorer 明显花钱。假设 9 个账号、工作日每天冷加载概览 10 次（累计消费
走 15 分钟缓存，近 30 天成本走 2 小时缓存）、运营看板 5 次（2 小时缓存）、账号页的
成本页签 10 次：

```
概览   约 (10 + 5) 次 × 9 账号 × $0.01 ≈ $1.35/天
看板   约 5 次 × 9 账号 × $0.01          ≈ $0.45/天（和概览共用的累计不重复算）
成本页 约 10 次 × 1 账号 × $0.01          ≈ $0.10/天
合计 ≈ $1.9/天 × 22 个工作日 ≈ $42/月
```

CloudWatch 各页按同样频率不到 $1/月，配额页签 $0。想再省就把 `CACHE_TTL`
调大（默认 900 秒）。

> 单价以 AWS 官方定价为准，可能随区域和时间变化。上面的 $0.01/次（Cost Explorer）
> 和 $0.01/1000 metric（GetMetricData）是写文档时的公开价格。

## 概览页

上面三张图，下面一面账号卡片墙。

| 图 | 说的是什么 |
|---|---|
| 额度使用 | 全部账号的累计消费 ÷ 额度合计（半圆仪表），下面是使用率最高的三个账号 |
| 近 30 天成本 | 每天一根柱，按账号堆叠（账号用邮箱前缀标），鼠标划到哪天看那天各账号的数，点图例只看一个账号 |
| 消费构成 | 各账号从启用日期起的累计消费，气泡大小按金额；气泡可以按住拖着玩，松手弹回去 |

每张卡片：

| 位置 | 来源 |
|---|---|
| 头像 | 默认是邮箱首字母；台账里填了别的（`AVATAR`）就用它的第一个字，底色见 `AVATAR_COLOR` |
| 头像旁边 | 主行邮箱（`EMAIL`），副行号码（`ACCOUNT`），再下面一排生命周期（Excel `LIFECYCLE`：正常、结算、风控……，只是标记）。没填邮箱时号码当主行 |
| 右上角 | 「查看详情」；卡片窄的时候（一行三张、侧边栏又开着）只剩箭头 |
| 三列 | 上游（`PARTNER`）、启用日期（`START_DATE`）、已启用几天；小字标签在上、数在下 |
| 客户 | 和上面三列一个样子：小字标签在上，小头像 + 名字在下；还没分给客户的写「库存」 |
| 最近调用 + 近 14 天的迷你柱 | CloudWatch，每个账号四个区合计 |
| 使用率、余额 | 累计消费 ÷ 额度；额度 − 累计消费 |
| 底部的大数字 | 累计消费 = 有标签的 CE 原价 × `TAG_RATIO` + 其余 × `UNTAG_RATIO` |
| 右下角 | 状态（活跃：近一小时有调用 / 已中断 / 无调用 / 异常：读不到 CloudWatch 或查不到消费，账号本身在报错，红色） |

状态和生命周期前面的小圆点一闪一闪（系统开了「减弱动画」就不闪）。

卡片上面最上一排是搜索框（搜邮箱或账号 ID），下面几排筛选签（生命周期、客户、状态，组内任选、组间
同时满足，和搜索框也同时满足），右边一个「刷新数据」（跳过缓存重查，和筛选签一个样子）。状态签上一个账号只落在一个状态里，几个签的数加起来就是全部。卡片
固定按「有问题的排前面」：异常 → 用量中断 → 其余，同一档里使用率高的在前。点卡片上任何地方
都进这个账号的页面。

一行几张按**屏幕**宽度定，不按内容区：1260 以上三张、1700 以上四张、2200 以上五张。开关侧边栏只让
卡片变宽变窄，不会一行三张变两张。

### 这一页没有日期筛选

**消费和余额都是「从这个账号的启用日期累计到今天」**，区间由台账的
`START_DATE` 列决定，不由用户选。

理由是额度这个东西是**一次性发的**：拿「本月消费」或「近 30 天消费」去比它，
比出来的数没有意义。要看的是「发出去的额度到现在用掉了多少」，那就只有一个
正确的区间。所以日期输入框和「本月 / 上月 / 近 7 天…」那排快捷按钮一并去掉了，
`WARN_PCT` / `DANGER_PCT` 两个阈值从此指的是「额度用掉的百分比」。

区间是**按账号各算各的**——两个账号启用时间不同，区间就不同。所以：

- 额度使用那张图的合计只是金额加总，**不代表同一个区间**。
- 卡片上写的是台账填的启用日期。**实际起算点和它对不上时**（没填、或早于 CE 保留期）
  卡片上会标出来，页面顶上也有一行说明。
- 想看某个时间窗口的消费，去账号页的「成本」页签。

### 累计区间不完整时会标出来

有两种情况会让累计消费**少算**、余额因此**偏高**，光看数字分辨不出来，所以对应
的卡片会标出来，页面顶部也给一条提示：

| 情况 | 实际起算点 | 行上的说明 |
|---|---|---|
| 台账没填 `START_DATE` | CE 最早可查日 | 台账未填启用日期，按 Cost Explorer 最早可查日起算 |
| `START_DATE` 早于 CE 保留期 | CE 最早可查日 | 启用日期早于 Cost Explorer 的保留期，更早的消费查不到，余额偏高 |

还有一种是台账被手改成了未来日期，区间会退化成今天一天（页面上的表单会拦住，
但直接改 Excel 拦不住）。

### Cost Explorer 能查多早：14 个月**含当月**

`earliest_queryable()` 算的是「当月往前数 13 个月的 1 号」，不是 14 个月。
这个差别是拿真实账号量出来的：2026-09-13 这天，起点填 `2025-08-01` 能查
（当月 + 前 13 个月 = 14 个月），填 `2025-07-01`、`07-13`、`07-14` 全部报

```
ValidationException: You haven't enabled historical data beyond 14 months.
```

早先写成 `month_shift(today, -14)`，实际要了 15 个月，一律被拒。以前只有手填一个
很早的开始日期才踩得到，现在「未填启用日期」的默认路径每次都要走这里，所以必须算对。

### TAG 列怎么写

`TAG` 列决定这个账号怎么拆分，格式是 `标签键=标签值`（`:` 和 `$` 也认）：

| TAG 列内容 | TAG 消费 | UNTAG 消费 |
|---|---|---|
| `map-migrated=migXYT8EVQSVP` | 该标签**等于这个值**的消费 | 其余全部（空值 + 其他值） |
| `map-migrated`（只给键） | 该标签**任意非空值**的消费 | 标签为空/缺失的消费 |
| 留空 / 没有 `TAG` 列 | 同上，标签键取 `.env` 的 `TAG_KEY` | 同上 |

两种口径下 **TAG + UNTAG 恒等于账号总消费**，不会有消费被漏掉。每个账号可以用不同的标签键和值。

> 写死标签值时，如果该区间内一分钱都没匹配上，数据层会算出一条提示（`CostSplit.note`），
> 内容是「台账里的值没匹配上，该区间实际出现过的值是 X、Y」——MAP ID 打错一个字符，
> 全部消费会被按 `UNTAG_RATIO` 加价，金额悄悄虚高。
>
> **这条提示目前不在页面上显示**：实际用起来它绝大多数时候只是在说「这段时间没有
> MAP 流量」，属于常态而非异常。逻辑和字段都留着（`cost_explorer._query` 里两个分支、
> `report.py` 的传递），想恢复就在卡片上把 `row.note` 显示出来。

（日期范围的选择只在账号页的成本、用量、预估三个页签上，**最早只能选到这个账号的
启用日期**——选得更早会自动从启用日期起算并说一声。Cost Explorer 只保留约 14 个月
历史数据，更早的开始日期同样会被收窄。）

## 客户 `/customers/`

每个账号属于一个客户（台账的 `CUSTOMER` 列写客户编号，空着就是**库存**），一个客户可以有多个账号。
客户本身存在台账的 `CUSTOMERS` 工作表里（编号、名字、国家 / 地区、头像、状态、开始合作的日期、备注），
客户时间线上手动记的事存在 `EVENTS` 工作表里，都跟着 `cred.xlsx` 一起备份、一起拷走，也能直接在
Excel 里改。第一次在页面上建客户、记事件时才把这两张表建出来，老台账不用动。

### 账号在客户名下的阶段

    库存 → 使用中 → 风控 · 待替换 → 待结算 → 已结算

阶段不单独存，按台账算：`SETTLED` 列有日期是**已结算**；生命周期里有「结算」、或者额度用完了是
**待结算**；有「风控」是**风控 · 待替换**；其余是**使用中**。所以在账号管理里给账号打上 / 去掉这两个
标签，客户页上的阶段跟着变（时间线上也记一笔）。客户页上的动作会顺手改生命周期：标记风控加「风控」，
替换、结算加「结算」；分配、换上来的新账号去掉上一段合作留下的「结算」，没有「风控」的标上「正常」。
**「风控」不会被分配抹掉**：那是 AWS 那边的事，分给哪个客户都还在，分过去就是「风控 · 待替换」，不算进
预算和余额；分配、替换的账号清单里，风控的标红、排在最后。要取消就在客户页「取消风控」，或者在账号管理
里改生命周期。

一个账号只属于一个客户。分错了可以**解绑**（客户页的「名下账号」里，或者账号管理的修改弹窗里把客户
改成「库存」），它的消费就不再算进这个客户，时间线上留一条记录。

**恢复使用**：AWS 解除了风控、换下来的账号还要接着用，在「名下账号」的「更多」里（账号页的页头上也有）
点「恢复使用」：生命周期去掉「风控」「结算」、标上「正常」，回到使用中，没用完的额度重新算进预算和余额。
就当它没离开过：对账单上之前那次「移出」不再算；时间线上之前的风控、替换都留着，再记一条「恢复使用」；
换上来的新账号不受影响，两个都在用。已经结算的不能恢复（线下对完账了，要再用就先解绑回库存再分配）；
只是额度用完的也不行，先调整额度。恢复以后又被风控，从新的那次算起。库存里打着「风控」的账号在账号页
也能恢复，只改生命周期。

### 名下账号

表格默认使用中的在上面，然后是风控、待结算、已结算（同一档里先分配的在前）。上面能按阶段筛（只列有账号
的阶段）、搜邮箱或 ID；点表头（账号、阶段、额度使用、分配）排序：升、降、再点回到默认。「分配」写全日期
（2026-10-01），替换上来的下面写着替换了谁。

### 近 24 小时调用

账单（Cost Explorer）要晚 1~2 天，客户页「每天消费」「还能用几天」下面一整行是 CloudWatch 的调用次数：
近 24 小时的折线图，一个账号一条线（四区合计、每小时一个点），晚几分钟。线尾是这个账号的头像和最后一小时
的次数，一眼认出是谁；末值挨在一起的头像上下错开，拉一根细线连回线尾。图下面是头像对邮箱（两个账号可能是
同一个字母，外圈颜色就是它那条线的颜色）。最后一个点是上一个整点那一小时——没过完的这一小时不画，免得线尾
凭空塌下去。颜色和「每天消费」一样，一个账号一个颜色。只查还在用的账号（结算了、停用了的不会再有调用）；
一直没调用的不画线，在图下面点名；账号多过 8 个时，调用少的并成「其他」一条。要看更长、分模型、分区的，
去账号页的「用量」页签。

标题下面只写时间范围；调用次数旁边是**今日预估**：今天到现在的 token × 牌价（和账号页「预估」页签一个算法，
以账单为准），图下面每个账号写着它 24 小时的调用和今天的预估。只估这 24 小时里有调用的账号。

客户页的「账号」卡片是按阶段的横条（使用中、风控 · 待替换、待结算、已结算），长短按占全部账号的比例，名字
后面是这一档里的账号头像。

账号页「摘要」的「近 7 天调用」下面写着**今天预估花费**：token × 牌价（和「预估」页签一个算法），也是
晚几分钟，以账单为准。

### 钱怎么算

客户的**预算、消费、余额只算「使用中」的账号**：账号一被标记风控、换下或者额度用完，就从这三个数里
一起出去，它用掉的钱留在**历史消费**里。所以 预算 − 消费 = 余额 任何时候都对得上；**结算**只是确认
线下（商务、折扣、税务）都对完了，不改数字。没有充值：预算只会因为分配账号、给账号**调高额度**变多。

- **每天消费**、**近 7 天日均**、客户列表的近 30 天消费：每个账号只算它算这个客户的那几天——分过来那天起，
  到风控、换下、用完、结算的前一天。换下来的账号后来还有零星的账，不画进这个客户每天花了多少，也不把还能用
  几天拉短。**历史消费**、对账单、结算照样按这个账号全部的账算（上游按整个账号收钱）。
- **还能用几天** = 余额 ÷ 近 7 天（不含今天）的日均。日均不到半分钱当作最近没有消费；算出来超过一年的
  写「一年以上」，不写具体天数和日期（账号刚风控、只剩零星几分钱的时候，这个数是天文数字）。走势图的
  预测最多往后画历史的两倍长，画不到 0 的虚线停在右边，末端写用完的日期或者「一年以上」。
- **调整额度**（客户页的「调整额度」、账号页的「调整额度」、账号管理表格里额度旁边的笔，或者修改弹窗里
  改额度）都在时间线上记一条「调整额度」：日期、改前 → 改后、谁改的、精确到秒的时间。因为额度用完进了
  待结算的账号，加完够用了就回到使用中。
- 分给客户的日期晚于账号的启用日期时（上线那天把用了几个月的老账号分过来），按启用日期算：一个账号
  只属于一个客户，它启用以来的消费都算这个客户的。

### 月度对账单

两种看法，详情页最下面切换：

- **按月**：月初余额 + 新分配 ± 调整额度 − 消费 − 移出 = 月末余额。移出是账号被标记风控、换下或者
  额度用完那天它还没用完的额度。最后一个月的月末余额就是页面上的余额，对不上就说明数据有问题。
  一个月一行，数下面小字写几个账号；点月份展开，每个账号一行：这个月分配、调整、消费、移出各是多少
  （移出写着原因：风控、换下、用完）。从最早分到账号、或者最早有消费的那个月开始列——合作了几个月才
  分账号的，前面那几个月一行全是 0，不列。
- **按账号**：每个账号每个月的折算后消费，已结算的也列着。

「导出 CSV」是每个账号每个月一行，折算后和 AWS 原价都有，Excel 直接打开。

### 时间线

有人做的事（分配、替换、标记风控、结算、调整额度、解绑、记一笔）存在 `EVENTS` 表里，卡片是**虚线框**。
按数据就能看出来的事不存，每次现算，卡片是**实线框**：

- **开始上量**：分给客户以后，第一次有一天折算后消费 ≥ `RAMPUP_DAILY`（默认 $500）
- **上量终止**：上量以后连续 `STOP_DAYS` 天（默认 3）都低于 `STOP_DAILY`（默认 $50），记在第一天。
  最近两天 Cost Explorer 还没出完账，不算
- **恢复上量**：终止以后又有一天 ≥ `RAMPUP_DAILY`
- **额度 70% / 90% / 用完**：按账号自己的额度（`WARN_PCT` / `DANGER_PCT`），用完时账号进入待结算
- **AWS 邮件**：邮件告警认出的滥用、盗用、暂停三类（告警流水里这三类不会被裁掉）

账号不算了（风控、换下、用完、结算）以后就不再记它的上量、终止。点卡片可以改日期、删掉；自动记的
删掉以后不会再生成（`EVENTS` 表里记一行 `SOURCE=auto` 的改动）。

按类型筛是一排签；按账号筛是一个下拉，能搜邮箱或 ID（账号一多，一排签放不下，只写邮箱前半截也认不出）。

**记一笔**：备注、开始上量、上量终止、恢复上量只是记下来；选「标记风控」和名下账号里的「标记风控」一样，
要选账号（只能选使用中、待结算、还没打风控的），生命周期换成「风控」，从那天起不算进余额。

横轴从以前流到现在：滚进屏幕时实线从左往右画过去，事件一件件从左边滑进来，最后亮出「今天」；实线上
一直有一道光从以前流向现在。第一件事之前、今天之后是**虚线**（还没开始、还没发生），虚线也一直往右走。
系统开了「减弱动画」就不动。时间线的画法客户页、账号页共用（`static/timeline.js`）。

  哪天、谁、从多少调到多少。

## 运营看板 `/ops/`

> **先下线了。** 默认不注册这个页面，侧边栏和概览上也没有入口；代码和数据层（`ops.py`、
> `ops_report.py`、`templates/ops.html`）都留着、测试照跑。`.env` 里设 `OPS_DASHBOARD=1`
> 重启就回来。下面写的是打开之后的样子。

电脑上每天巡检用的一页，三块：

**经营汇总**

- 四张指标卡：收入、AWS 原价、毛利、毛利率，各带和上一段比的变化和逐日迷你柱。
- 近 12 个月：每月一根柱，底下 AWS 原价、上面毛利，整根就是收入。
- 额度：和概览同一份累计报表，外加累计毛利、超额 / 快用完 / 过半各几个。
- 明细：按上游、按账号两张表（可排序），收入、原价、毛利、毛利率、和上一段比、额度使用。

**风险与告警**

- 需要关注：一个账号一行，列出它的问题，最要紧的账号在前。问题包括超出额度、额度用到
  `DANGER_PCT` / `WARN_PCT`、查不到 Cost Explorer、用量中断、读不到 CloudWatch，以及
  打着红色（风控）或琥珀色生命周期标签。
- 最近告警：真正发到 TG 群的最近 12 条（`ALERT_EVENTS_PATH` 的流水），包括用量开始 /
  中断、额度预警、账号变动、AWS 邮件告警、日报。

**模型与用量**

- 全部启用账号 × 四个区的调用次数、输入 / 输出 / 总 token，和上一段比。
- 按模型、按区域的条形，条长是占全部调用的比例，下面一行写 token。

口径：

| | |
|---|---|
| 收入 | 按台账比率折算后的消费：有标签的乘 `TAG_RATIO`，其余乘 `UNTAG_RATIO`。比率就是加价 |
| 毛利 | 收入 − AWS 原价；毛利率 = 毛利 ÷ 收入 |
| 时间段 | 本月（比上月同期）、上月（比前一个月）、近 30 天（比前 30 天）、今年（不比：CE 按天只查得到 14 个月，够不着去年年初） |
| 起算 | 每个账号从启用日期算起，和概览一致 |
| 范围 | **只算启用中的账号**。停用的不再查 CE（省钱），所以长区间里已经停用的账号停用之前的收入不在里面 |
| 日子 | UTC 日期：CE 按 UTC 出账，CloudWatch 的按天数据也对齐 UTC 零点 |

时间段和「刷新数据」放在内容区左上，不放页头右边：右上角是报错弹窗的位置，报错一直
留着直到手动关，会盖住页头右边的按钮。

## 账号页 `/account/<号码>/`

一个账号一页，网址里就是账号号码，可以收藏、可以发给别人。和别的页面一样有标题「账号」，右边是
「调整额度」（就在这一页改：填加多少，减写负数，时间线上记一笔）和「编辑资料」（去账号管理页打开这个
账号的修改弹窗，改完、取消都回到这一页）。标题下面是「当前账户」（换账号：上面一行写「当前账户」，下面
一行是邮箱前缀 · 号码；点开能搜邮箱、ID 或生命周期，每个账号右边是它的生命周期；换账号停在同一个页签）。
打着「风控」「结算」、还没结算的账号，按钮前面多一个「恢复使用」（见《客户》里的「恢复使用」）。
再下面是账号资料：大头像、邮箱、状态（异常的标红），再下面两行：号码、上游、启用日期（第几天）；所属
客户、生命周期。

六个页签（配额放最后：第一次要拉 45 秒左右，也最少看）：

| 页签 | 路径 | 内容 |
|---|---|---|
| 摘要 | `/account/<号码>/` | 额度仪表、近 30 天成本、告警开关和群、近 7 天调用、配额前五、账号资料 |
| 成本 | `/account/<号码>/cost` | 按服务 / 标签分的成本，按日或按月（原来的「成本和使用情况」） |
| 用量 | `/account/<号码>/usage` | CloudWatch 的调用和 token（原来的「模型用量」） |
| 预估 | `/account/<号码>/estimate` | token × 牌价的当天估算（原来的「预估成本」） |

## 账号页 · 用量页签（CloudWatch）

命名空间 `AWS/Bedrock`，维度只用 `[ModelId]`，统计口径 `Sum`。从上到下：

1. **四张指标卡**：调用次数、输入 / 输出 / 总 Token，各带「和前一段同样长的时间比」的
   变化和一条小走势。指标卡就是页签：点哪张，下面的主图就画哪个指标。
2. **主图**：一张折线图，每个模型一条线，上面一排「四区合计 / 弗吉尼亚 / 俄亥俄 / 北加州 /
   俄勒冈」切换区域，每个视图带总数、占比、平均和峰值。
3. **三张小卡**：模型占比（气泡）、模型 × 区域（热力格，格子里写着数）、一周作息
   （星期 × 小时，看什么时候忙）。
4. **精简明细**：每个模型的总数、占比、各区的数、峰值。

区域不是筛选项：四个区一次全查，用页签切。合并成一条线会把跨区分布这个信息丢掉，
而这恰恰是 MAP 分发最该看的——实测四个区的量相当均衡（59.3 万 / 60.3 万 / 58.0 万 /
59.7 万）。

| 参数 | 取值 |
|---|---|
| 指标 | 点指标卡切换（单选） |
| 时间 | 一个下拉：近 1 小时 / 6 小时 / 24 小时 / 7 天 / 30 天，或自定义起止时刻；最早到启用日期 |
| 粒度 | 1 分钟 / 5 分钟 / 1 小时 / 1 天 |
| 标签 | 全部 / 仅有标签 / 仅无标签 |

指标是**单选**，因为调用次数和 token 量级差好几个数量级，画在双 Y 轴上时两个
刻度的对齐是任意的，会凭空造出一段不存在的相关性。要对比就切换着看——四张指标卡
同时摆着总数，不切也能比。

这个账号四个区全都读不到 CloudWatch 时，指标卡写「—」和「读不到 CloudWatch」，不写 0：
读不到不等于没调用。

默认窗口是 7 天而不是 24 小时：这类 MAP 分发流量是突发的，中间可能空置一两天，
默认 24 小时经常一开页就是空图。

### 两个口径都不会重复计数

这几条是拿真实账号实测确认过的，不是推测：

- 把所有 `ModelId` 的 `Invocations` 相加，**正好等于**不带维度的账号级总量
  （318,978 = 318,978，差 0）。所以逐模型求和既不重复也不漏。
- `[ModelId, ContextWindow]` 是 `[ModelId]` 的**子集**（1M 上下文约占 7%），
  属于细分而不是独立的流。代码只取「维度恰好只有 ModelId」的那一组，
  绝不把两者相加。
- 原厂模型流（`global.anthropic.*`）和应用推理配置流（12 位不透明 ID）
  **互不相交**：走配置的流量只记在配置上。所以把配置归并到底层模型是无损的，
  两种口径的总量必然一致（有测试守着这条）。

### 有标签 / 无标签怎么判定

CloudWatch 的指标**不带成本分配标签**，所以这个区分是推断出来的——但推断有据可查，
不是猜的。`ModelId` 有两种形态：

```
global.anthropic.claude-opus-4-8   直连原厂 / 跨区模型
2kbsta0lwebx                       应用推理配置（12 位不透明 ID，不是完整 ARN）
```

实测确认：**应用推理配置上带着 `map-migrated` 标签，且值与台账 `TAG` 列一致**
（两个账号各 11 / 9 个配置全部带），而直连调用没有任何标签。于是

```
走推理配置的调用  ->  有标签
直连模型的调用    ->  无标签
```

判定读的是 `bedrock:ListTagsForResource` 返回的真实标签，**不靠配置名猜**——不同
账号的命名规则完全不同（`map-global-claude-opus-4-8-use1` vs
`claude48oupsauto_0706`）。匹配规则与 `cost_explorer` 完全一致：台账把值写死了就
要精确相等，只给键就是任意非空值。所以某个配置打了别人的 MAP ID，在这里同样算
无标签。

图例**始终按模型**分线（配置归并进它的底层模型），标签只决定算哪部分流量：

- **全部**（默认）：不过滤。
- **仅有标签** / **仅无标签**：只保留对应那部分。

**汇总处的「有标签」「无标签」两块始终显示全量拆分，不跟着上面的筛选走**，所以切到
「仅无标签」时也能看到被排除掉的那部分有多少（这两块左侧有一道蓝色竖线，并标注
「不受上方筛选影响」以免误读）。

标签读不到时（缺 `bedrock:ListTagsForResource` 权限）所有流量都会落进「无标签」，
这会让筛选变得毫无意义，所以页面会明确提示而不是默默给出错误结论。

#### 和成本页对照

同一区间（本月至今）两侧的「有标签」占比：

| 口径 | 有标签占比 |
|---|---|
| Cost Explorer 原始金额 | 85.02% |
| CloudWatch 总 Token | 90.58% |

差 5.56 个百分点，**方向是对的**：成本按各模型单价加权（Opus 和 Haiku 差几十倍），
而无标签流量全部集中在最贵的 `claude-opus-5` 上，所以它占钱的比例自然高于占
token 的比例。不该期待两个数字相等。

### 粒度会被自动收窄

CloudWatch 对不同 Period 的保留期不同，超期的数据是**查不到**而不是返回 0：

| 粒度 | 保留期 |
|---|---|
| 1 分钟 | 15 天 |
| 5 分钟 | 63 天 |
| 1 小时 | 455 天 |
| 1 天 | 455 天 |

选了「近 30 天 + 1 分钟」会自动调到能查得到、点数也不爆的档位，并在页面上说明
调了什么。每条序列最多 1500 个点（`GetMetricData` 单次请求有 100,800 个数据点
的硬上限）。

结束时刻会对齐到 Period 边界，所以末桶总是完整的——不会出现「当前这一小时才过
了几分钟」导致最后一个点凭空塌下去的假象。

### 图表

折线图同样是手写 SVG（`chart.render_lines`），和别的图共用同一套 8 色板。

- 平滑曲线（单调三次插值，不会冲出数据范围），线下一层从线往零线渐隐的填充；
  点超过 400 个就画折线——那个密度下看不出区别，HTML 却要大好几倍。
- 时间轴刻度只落在整点、整天上，两个刻度之间至少留 88px，不会密密麻麻挤在一起。
- 悬浮用一个覆盖绘图区的透明层配合「取最近点」，而不是逐列命中区：点可以多到
  1500 个，逐列命中区会窄到点不中。一条虚线准线跟着鼠标，每条线上一个白圈圆点，
  提示框是白底、挨着准线，值在前名字在后、大的在上。键盘可以 Tab 进图表，用左右
  方向键逐点浏览，`Home`/`End` 跳到两端，`Esc` 关闭。
- 悬浮数据是紧凑格式（每条序列一串值和纵坐标），五个区域视图的页面因此从 600 多 KB
  降到 370 KB 左右。脚本在 `static/app.js`，凡是带 `data-line-src` 的图都能用。
- 同一个模型在五个视图里是同一个颜色：序列集合和颜色槽在数据层就统一好了，按四区
  合计排名决定保留哪 8 条。全为零的序列不画贴地直线，否则底部会糊成一片。

## 账号页 · 配额页签

一张表，一行是**这个账号的一条应用推理配置（ARN）**，配上它的底层模型和**该区域**
的 TPM / TPD：

| ARN ID | 账号 | 模型名称 | 模型 ID | 区域 | TPM | TPD |
|---|---|---|---|---|---|---|
| `obc6dxcudai0` | `590575330322` | Claude Opus 4.6 V1 | `anthropic.claude-opus-4-6-v1` | `us-east-1` | 6,000,000 | 8,640,000,000 |
| `xzgy29svdq5y` | `590575330322` | Claude Opus 4.6 V1 | `anthropic.claude-opus-4-6-v1` | `us-east-2` | 3,000,000 | 4,320,000,000 |

两个筛选：**模型名称**、**区域**，改动即提交。筛选只裁行，不重新拉数据——所以在
缓存有效期内切筛选是毫秒级的。

默认行序是 **模型（按最高 TPD）→ 区域**，同一模型的四个区相邻、组首一道
细分隔线。**表头可点排序**：一次升、再一次降、第三次回到这个默认顺序。排序在
客户端做（不走一次往返；脚本在 `static/app.js`，凡是 `table[data-sortable]` 都能用，
账号管理页、运营看板的明细也是它），几个刻意的处理：

- **每次都从默认顺序重排**，不是在上一次结果上再排。所以「降序」是默认顺序的真
  反转，同值行之间的相对次序也稳定。
- **空值永远沉底，不跟着升降翻转。** 「未列出」不是 0，「无权限」也不该按空字符串
  排到最前面。
- **排序值不取渲染出来的文字。** 显示的是 `43,200,000,000` 和「未列出」，按文本排
  必错，所以每个单元格上标了 `data-sort` 作为规范值（数字是未格式化的原值）。
- **排序期间隐掉分组线。** 「同一模型的四个区相邻」这个前提只在默认顺序下成立，
  自定义排序后线会散落在没有意义的位置。
- 箭头由 `aria-sort` 驱动，无障碍属性和视觉共用一个来源。表头可 Tab 聚焦、
  回车 / 空格触发。

ARN 来自 `bedrock:ListInferenceProfiles` 的 `typeEquals=APPLICATION`——也就是账号
自己建的、CloudWatch 指标里以 12 位不透明 ID 出现的那些配置。TPM / TPD 来自
Service Quotas（`ServiceCode=bedrock`）的这一对：

```
Global cross-region model inference tokens per minute for <模型>   -> TPM
Global cross-region model inference tokens per day    for <模型>   -> TPD
```

这一页只展示配额本身，不查实际用量——用量在「用量」页签。

### 实测确认的几件事

- **「Global cross-region」配额已经不再四区相同了。** 名字里写着 Global，但
  **提额是按区批准的、不会自动铺开**：实测 Claude Opus 4.6 V1 在 `us-east-1` 是
  6.0M TPM / 8.64B TPD，`us-east-2` / `us-west-1` / `us-west-2` 还是 3.0M / 4.32B。
  所以四个区必须各查一次。页面把没跟上提额的行标黄，卡片头上数一共几个模型不一致。
  > 这条推翻了本页早先的做法（挑 `us-east-1` 问一次当成全局值）。那样另外三个区
  > 显示的数字是错的。
- **应用推理配置是按区域创建的**：同一个模型在四个区各有一条独立 ARN，12 位 ID
  互不相同。所以区域是 ARN 自带的维度，不是拼上去的。
- **「最高值」必须按账号分组判定。** 配额池是按账号独立发的，实测两个账号同一个
  模型的额度就不一样。只按模型分组的话，会拿账号 A 的 6M 去判账号 B 的 3M
  「没跟上提额」，凭空标出一片黄——那是两个互不相干的池子。
- **配额口径是输入 + 输出 token 合计**，覆盖 Converse / ConverseStream /
  InvokeModel / InvokeModelWithResponseStream。
- **两条配额的可调性不一样**：TPD `Adjustable=false` 改不了，TPM
  `Adjustable=true` 可以在 Service Quotas 控制台申请提额。所以 TPM 撞上限时是有
  办法的，TPD 撞上限只能找 AWS——而且**申请时四个区要各提一次**，上面那条说的
  就是漏提的后果。
- **`bedrock:ListFoundationModels` 实测两个账号都被组织 SCP 拒了**，拿不到 AWS 的
  官方模型名。所以「模型名称」一列取自配额名（`Anthropic Claude Opus 4.6 V1`
  去掉厂商前缀）——反正配额本来就是按这个名字发的。
- **「模型 ID」取自 ARN 自己声明的 `modelArn`**，不是从配额名或配置名拼的。
- **配置名（`claude46Oupsauto_wjc_0529`）是账号自己起的，和模型名没关系**，两个
  账号的命名规则也完全不同，所以模型名绝不从配置名猜。
- **1M 上下文长度是独立的一条配额**，不和同名模型共享额度。它没有对应的应用推理
  配置，所以出现在下面那张「有配额，但账号下没有应用推理配置」表里。

### 读不到 ARN 时会降级

`bedrock:ListInferenceProfiles` 可能被组织 SCP **显式拒绝**（实测有账号四个区全拒）。
这时表格退回按「模型 × 区域」列配额，ARN 和模型 ID 两列显示「无权限」，配额数字照常
——那是 `servicequotas` 的权限，另一套。页面上一行浅色说明，右上角的报错写清是
「被组织的 SCP 显式拒绝」，「查看详情」里有 AWS 原话和策略 ARN，可以直接拿去改。

### 「有配额，但账号下没有应用推理配置」

主表是按 ARN 列的，所以有配额、但没建配置的模型会从主表里消失。这些模型只能直连
原厂模型 ID 调用，**流量不会带上台账里那个成本分配标签**，在「用量」页签会算成
无标签流量。所以单独列一张小表兜住，免得悄无声息。

### 性能

`ListServiceQuotas` 必须显式设 `PageSize=100`：boto3 的默认分页每页只有 8 条，
1162 条配额要发 146 次请求，实测 54 秒；设成 100 之后是 30 页。限流会吃掉重试
次数，所以这条通路的 `max_attempts` 单独放宽到 8——用默认的 3 次，某个区被限流
打穿之后整列数据就没了。冷加载 40～50 秒的原因见《各页面的 API 调用与费用》。

### IAM 权限

在原有权限之外再加一项 `servicequotas:ListServiceQuotas`，见开头的
《AK/SK 需要什么权限》。这个接口不计费。

## 账号页 · 预估页签

Cost Explorer 的数据有一到两天延迟，今天花了多少要等到后天才看得见。这一页用
CloudWatch 的 token 量乘 AWS 牌价，立刻给出估算：

```
估算成本 = 输入×输入价 + 输出×输出价 + 缓存读×缓存读价 + 缓存写×缓存写价
```

页面上有两块：**每天的预估花费**（按模型分色的堆叠柱状图）和**按模型明细**
（四种 token 的量、四种单价、估算成本）。

### 准不准

2026-08 拿一天 10 万美金的真实账单逐模型核对过：

| 模型 | CE 实际 | 预估 | 比值 |
|---|---:|---:|---:|
| Claude Opus 5 | 47,191.50 | 47,135.96 | 0.999 |
| Claude Opus 4.6 | 30,783.30 | 30,779.33 | 1.000 |
| Claude Opus 4.8 | 15,762.44 | 15,758.52 | 1.000 |
| Claude Sonnet 4.6 | 4,248.45 | 4,248.20 | 1.000 |
| Claude Opus 4.7 | 2,554.61 | 2,554.32 | 1.000 |
| Claude Sonnet 5 | 1,886.17 | 1,884.54 | 0.999 |
| **合计** | **102,428.12** | **102,362.51** | **0.999** |

**误差 0.06%。**

### 四个计数器互相独立，不要减

`InputTokenCount` **不包含**缓存读写的 token。这一点是实测的：某天输入 32 亿、
缓存读 765 亿——缓存读比输入大 24 倍，输入那一项不可能包含它。所以公式里输入
直接乘单价，不用先减掉缓存。

写成「(输入 − 缓存读 − 缓存写) × 输入价」的话，输入会算成负数，整体偏低 6~26%
（实测各模型 0.74~1.01 不等，没有规律）。

### 跨区和本区是两个价

Global（全球跨区推理）比本区便宜约 10%。哪一档由数据自己说了算：

- **直连模型**看 ModelId 前缀：`global.anthropic.*` 是跨区；`us.` / `eu.` 之类的
  地理级跨区走本区价。
- **应用推理配置**看 `modelArn` 里有没有不带区域的那一条
  （`arn:aws:bedrock:::foundation-model/...`）——跨区配置会带上它。
  刻意不看配置名：不同账号命名规则完全不同，猜名字迟早出错。

判错的话整体会稳定偏 10%，很好识别。真判错了可以用 `PRICE_TIER` 强制覆盖，
不用改代码。

> 注意 AWS 并非对所有模型都给跨区折扣——实测 Claude Sonnet 4 两档价完全相同。

### 单价从哪来

AWS Price List 的**公开批量端点**，service code 是 `AmazonBedrockFoundationModels`：

```
https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/
    AmazonBedrockFoundationModels/current/us-east-1/index.json
```

**不需要任何凭证，也不需要给账号加 `pricing:GetProducts` 权限。** 文件 0.4 MB，
按天缓存，本地留一份副本（`bedrock-prices.json`），AWS 端点临时不可达时用副本顶上
并在页面上提示。

几个容易踩的点：

- Claude **不在** `AmazonBedrock` 这个 service code 里。那里面只有 5 条 Claude 2.x/3
  时代的老 SKU，现役模型一条都没有。
- `servicename` 恰好就是 CE 里的计费条目名（`Claude Opus 5 (Amazon Bedrock Edition)`），
  所以两边能逐模型对账。
- `usagetype` 有**两代命名**：老的 `InputTokenCount`，新的 `input_tokens_standard`，
  不同世代的模型混着用，两套都得认。
- **四个美区单价一致**（有用例守着），所以只拉 us-east-1 一份，四区合并计价是安全的。

### 已知的偏差来源

| 来源 | 方向 | 说明 |
|---|---|---|
| **AWS 公开牌价** | 偏高 | 不含 EDP 或私有折扣。有协议价的话实际账单会更低 |
| **1M 上下文** | 偏低 | 该档单价更高，但 AWS 价目表里没有对应 SKU，无从取值 |
| **缓存写档位** | 偏低 | 1 小时档比 5 分钟档贵 60%，CloudWatch 只有一个计数器区分不了。实测按 5 分钟档能对上账单，说明这部分占比很小 |
| **新模型** | 偏低 | 价目表里还没有的模型会被标成「无单价」，**不计入总额**，页面上会明确列出来 |

这一页**不套**台账的 `TAG_RATIO` / `UNTAG_RATIO`，出来的是 AWS 原始成本，不是加价后
的对外金额——要和额度比请看概览页。

## Cost Explorer 查询口径

- **指标**：`UnblendedCost`（可在 `.env` 改成 `AmortizedCost` / `NetUnblendedCost`）
- **服务范围**：账号下全部服务，不加服务过滤
- **拆分方式**：按 `TAG` 列里的标签键做 `GroupBy`，再在本地按标签值归类。一个账号一次 API 调用就能同时拿到 TAG 和 UNTAG 两部分。
- **端点**：`us-east-1`（Cost Explorer 是全局服务）
- **凭证**：每个账号用台账里自己的 `AK` / `SK`，权限见开头的《AK/SK 需要什么权限》

> ⚠️ 注意：Bedrock 上的 Claude 在 Cost Explorer 里是**按模型独立计费条目**，服务名形如
> `Claude Opus 5 (Amazon Bedrock Edition)`，**不叫** `Amazon Bedrock`。
> 所以如果要启用 `SERVICE_FILTER`，必须填这些模型级的服务全名，否则会查出 0。

## 设置 `/settings/`

侧边栏最下面（退出上面）。平台自己的记录，只读：

- **操作日志**：台账的每一次改动，谁、什么时候、改了什么——就是台账旁边的 `ledger-audit.log`，
  凭证的值从来不写进去。账号写成「邮箱（号码）」，客户写成「名字（编号）」，带日期的动作（分配、标记风控、
  替换、结算、调整额度、记一笔、恢复使用）写上选的那天；时间线上改日期、删掉写着是哪一条（类型、账号、
  原来的日期）。能搜（搜账号号码、邮箱、客户名）、按类别筛（账号、客户、标签、告警）；说明里的账号号码
  点了去那个账号的时间线。只读日志最后 5000 行，一次列 500 条。以前写下的老日志还是原来的样子。
  网页上的改动最后多一列 **IP**（设置页上写在「谁」下面，是你自己的标一个「你」，也能按 IP 搜）：大家共用一个
  账号、别的平台一键登录进来的也是它时，光写用户名分不出是谁。命令行、定时任务改的没有 IP。「改了什么」里的
  换行、制表符换成空格，多行的客户备注不会把一行日志拆开。
- **登录记录**：每次登录成功、失败、被锁定、退出，时间、用户、IP、来源、浏览器；上面是近 30 天的成功、
  失败次数和登录过的 IP 数。存在 `LOGIN_EVENTS_PATH`（默认 `login-events.jsonl`），只留最近 1000 条。
  **不记密码**；用户名照记，登录失败的那一行写着输进来的用户名（红字），看是谁在试、试的什么名字。
  要知道：有人把密码错填进用户名框的话，那一次的「用户名」就是密码，会出现在这里。
  **来源**：别的平台「一键登录」是替用户从浏览器提交登录表单，浏览器会带上那个平台的网址（Origin，没有就看
  Referer），这里记下是哪个网站；本站登录页提交的写「本站」。IP 是用户自己的 IP（表单是从他的浏览器提交的），
  不是那个平台服务器的。来源这个头能伪造，只当参考，IP 才靠得住（跑在 Nginx 后面要开 `TRUST_PROXY`，见 DEPLOY.md）。

## 账号管理页 `/accounts/`

台账的增删改都在这一页，不用再手工改 Excel 再传上去。表格里没有输入框，
改字段都走弹窗，避免手滑碰到输入框就改了数据。在表格里点一下就生效的只有几个
**可逆**的动作：恢复、TG 告警开关、邮件告警开关、生命周期、额度。

表格一行一个账号：账号（头像 + 邮箱 + 号码，邮箱点了去这个账号的页面）、上游、生命周期、
状态（缺凭证的标出来；掩码后的 AK 在这一格的悬停提示里）、启用日期、额度、比率
（TAG / UNTAG，悬停看标签依据）、两个告警开关、操作。上面一排筛选：搜索（邮箱、号码、
上游）、上游、状态、告警，再一排生命周期签；全在浏览器里筛，选择记在这个标签页里，
改完东西整页刷新回来还是这个筛选、还停在原来的位置。表头可点排序。

| 操作 | 入口 | 说明 |
|---|---|---|
| 新增 | 页面右上角「＋ 新增账号」 | 弹窗里填账号 / **账号邮箱** / 上游 / 额度 / 启用日期 / 两个比率 / TAG / 生命周期 / 头像 / **AK / SK**，可选再填告警邮箱和 TG 群组 ID，追加在末尾，不影响已有行。生命周期默认勾着「正常」 |
| 修改 | 每行右侧的铅笔图标 | 弹窗里改，**没有 AK/SK 这两项** |
| 改生命周期 | 「生命周期」列的铅笔（鼠标划到那一行才露出来） | 一个小弹层里多选，保存后表格原地更新、不整页刷新，只写 `LIFECYCLE` 这一格 |
| 改额度 | 「额度」列数字左边的铅笔（同上，划到那一行才露出来） | 小弹层里填新的额度（可以写一句说明），保存后那一格原地更新，只写 `BUDGET` 这一格；时间线上记一条「调整额度」 |
| 管理标签 | 页面右上角「生命周期标签」 | 增删可选的标签、挑颜色；删一个标签，打了它的账号上一起去掉（要点两下才删） |
| 停用 | 每行右侧的电源图标 | 先弹确认窗说明后果，点「确定停用」才真的写。软删：只把 `ENABLED` 列置 FALSE |
| 恢复 | 停用的行右侧的回退图标 | 停用的账号在这一页仍然可见。恢复是安全可逆的，不再拦一道确认 |
| 删除 | 每行右侧的垃圾桶图标 | 确认窗里要**再输一遍登录密码**。整行清空、不能恢复，见《删除意味着什么》 |
| TG 告警开关 | 「TG 告警」列的开关 | 点一下立刻写台账，**只翻 `TG_ENABLED` 这一格**，群组 ID 不动。还没填群组 ID 的账号开关是灰的，先去修改弹窗里填 |
| 邮件告警开关 | 「邮件告警」列的开关 | 同上，只翻 `MAIL_ENABLED`。还没填好告警邮箱的账号开关是灰的，见《邮件告警》 |

新增和修改弹窗分三页：**基础信息**、**告警邮箱**（可选）、**Telegram 告警**（可选），页签名字
前面各有一个小图标（证件、信封、纸飞机）。基础信息里账号邮箱排在账号 ID 前面，打开时光标落在
邮箱上。三页在同一个表单里，切页只是换一页显示，哪一页上点「保存」都是三页一起提交；每次打开
都从基础信息开始。弹窗按最高的那一页定高，切页时底部的按钮不跳。几处照顾：

- 点「保存」时有必填项没填、而它在另一页上：先翻到那一页再提示，不会看上去像按钮没反应。
- 校验没过时弹窗停在第一条错误所在的那一页，有错的页签上标一个红点；错误清单在页签
  上面，哪一页都看得到。
- 点完「发测试消息」「测试连接」回来，停在测试的那一页。
- 页签上可以按左右方向键换页。
- 输入框里按回车 = 点底部的「保存」（新增弹窗是「添加账号」）。浏览器默认会去点表单里的
  第一个提交按钮，那是藏在告警邮箱页里的「测试连接」——不接管的话，回车会去登录一次邮箱。
  输入法选字时的回车不算。

保存之后右上角说一句「已保存」，后面灰字是哪个账号（邮箱），下面一行是改了哪几项，用页面上
的叫法（「改了额度和启用日期」），不写 Excel 表头；审计日志照旧按列记改前改后的值。停用、恢复、
开关、删除、改生命周期也是这个样子：粗体一句话 + 哪个账号 + 需要的话一行说明。

操作列只放图标，鼠标悬停有文字提示，读屏读的是 `aria-label`（「修改 jeff@example.com」
「停用 jeff@example.com」，没填邮箱的用号码），不会只念一声「按钮」。

TG 告警的开关**只在表格里有**，修改 / 新增弹窗里只管群组 ID：

- 弹窗保存**不碰** `TG_ENABLED`。旧页面或手搓的请求带着 `tg_enabled` 提交上来也不算数。
- 新增账号时填了群组 ID，开关直接打开——填群本身就是「要往这些群发」的明确表态，群里
  马上收到「新账号启用」；没填群就是关。
- 在弹窗里把群组 ID 全删掉，会顺带把开关关掉（开着却没处发没有意义）：保存后的提示里说
  「群组 ID 全删了，TG 告警跟着关了」，审计日志里写「TG_ENABLED 开 → 关（群组 ID 全删了）」。

开关旁边不放字。填了几个群、账号已停用、服务器没配 Token 这些都在开关的悬停提示里；
没配 Token 又有账号开着告警时，页面顶上会有一条提示，不是每行各挂一个。

弹窗用的是浏览器原生的 `<dialog>`，遮罩、ESC 关闭、焦点陷阱都是浏览器自带的。
点遮罩、点右上角 × 、点「取消」都只是关窗，不会写任何东西——**只有弹窗里那颗
主按钮会提交**。校验没过时，对应的弹窗会带着错误提示和你刚填的值自动弹回来，
不用重新输一遍。

> 这一页依赖 JavaScript。关掉 JS 只能看，不能改（页面上会有提示）。别的页面不受影响。

### 账号邮箱、生命周期、头像

- **账号邮箱**（`EMAIL`）新增和修改时必填，格式要对，两个账号不能填同一个（不分大小写，
  停用的也算）。各页面、下拉框上邮箱是主行、号码是副行，TG 卡片上两个一起写。告警邮箱的地址留空、只填
  密码时，收的就是账号邮箱。
- **生命周期**（`LIFECYCLE`）是纯标记：正常、结算、风控……一个账号可以打多个，不影响任何
  查询、汇总和告警。概览和账号管理页都能按它筛，运营看板把打着红色（风控）、琥珀色标签的
  账号列进「需要关注」。可选的标签在台账的第二个工作表 `LIFECYCLE`（`NAME`、`COLOR` 两列）
  里，和账号一起备份、一起拷走；没有这张表就是默认的正常 / 结算 / 风控，第一次在页面上增删
  标签时才建出来。
- **头像**默认是账号邮箱的首字母，底色按邮箱自动配（同一个账号在哪个页面都是同一个颜色）。
  弹窗里可以换成一个字或表情（`AVATAR`），也可以自己挑八组底色之一（`AVATAR_COLOR`，0～7）。
  圆圈里只放**一个字**：填了一串（「Johanna」、几个表情）只取第一个，按人眼看到的算——带肤色
  的表情、国旗、ZWJ 拼起来的家庭表情都算一个（`avatars.first_grapheme`）；字母转成大写。
  保存时就只存那一个字。

### 凭证是单向的

AK/SK 只在新建时填一次，此后既不回显也不可改——页面上只看得到掩码后的 AK
（`AKIA…7X4Q`），SK 任何时候都不出现在 HTML 里。

**要换凭证就停用旧账号、新建一条。** AWS 换 AK 本来就是签发新的、作废旧的，
做成原地编辑反而容易停在半新半旧的状态。

### 停用意味着什么

停用的账号**从概览和运营看板里消失**，不再参与额度合计，概览和看板也不再为它产生
Cost Explorer 请求（省钱）。账号页还能打开它（页头标「已停用」，账号选择器里排在
「已停用」一组），账号管理页照常可见。

行不会被删除，所以：

- 其他账号的行号不动，`account.key`（`账号#行号`）不会集体位移，各处按它建的
  缓存键和页面上的书签都还有效；
- 凭证和 TAG 配置原样保留，恢复之后立刻能用；
- 被停用的账号 ID **不能**被新建的账号重新占用，否则恢复时就撞车了。

### 删除意味着什么

停用够用的时候就用停用。删除是给「这个账号以后都不会再用了」准备的：

- 台账里这一行**整行清空**——额度、比率、TAG、AK/SK、TG 群组 ID、告警邮箱全部删掉，
  不能在页面上恢复；它从所有页面消失，也不再发任何告警。
- **行本身不删**，清空的那一行空着留在原处：和停用同一条底线，其他账号的行号不动、
  `account.key` 不位移。以后新增的账号照常追加在最后。
- 同一个账号 ID 删掉之后**可以**重新新增（停用的不行）。
- 确认窗里要**再输一遍登录密码**。输错按登录失败计数、和登录页共用同一个锁定，拿到一个
  没退出的会话也不能靠这里一遍遍试出密码；密码不进日志，也不回填。
- 删除不备份（见下一节）。真删错了，最近一次新增或修改时留的备份里还有这一行。

### 每次写入都会做的事

1. 校验（账号 12 位数字且台账内唯一、账号邮箱必填且唯一、额度非负、启用日期能解析且不晚于今天、比率大于 0、TAG 能解析出标签键、生命周期在清单里）；
2. **新增和修改账号**时，先备份当前台账到 `ledger-backups/cred-<时间戳>.xlsx`，只保留最近
   20 份。TG / 邮件告警开关、生命周期、停用 / 恢复、删除**不备份**——只留 20 份，点几下开关
   就会把改字段之前的那几份挤掉；
3. 写到同目录的临时文件，再 `os.replace()` 原子替换——中途崩了不会留下半个文件；
4. 清掉台账缓存，并往 `ledger-audit.log` 追加一行「谁、什么时候、改了什么」（不含凭证值）。
   不备份的那几种也照样记。

没有任何字段真的变化时（比如点了保存但什么都没改），第 2~4 步整个跳过，文件的
mtime 都不会动。

> `ledger-backups/` 里是**明文 AK/SK 的完整副本**，和 `cred.xlsx` 同等敏感。
> 已经在 `.gitignore` 里，权限也是 640。

### 手工改 Excel 还能用吗

能，格式没变。表头大小写、前后空格、**列顺序**都不敏感，多余的列会被忽略：

```
必需：PARTNER  ACCOUNT  BUDGET  TAG_RATIO  UNTAG_RATIO  AK  SK
可选：TAG  ENABLED  START_DATE  TG_ENABLED  TG_CHAT_IDS
      MAIL_ENABLED  MAIL_PROVIDER  MAIL_ADDRESS  MAIL_PASSWORD  MAIL_SERVER
      EMAIL  LIFECYCLE  AVATAR  AVATAR_COLOR
第二个工作表（可选）：LIFECYCLE，两列 NAME  COLOR
```

`EMAIL` **老台账没有这一列也能读**，页面上显示「未填账号邮箱」；下次修改这个账号时要补上。
`LIFECYCLE` 一格里多个标签用逗号隔开，全角逗号、顿号、分号、竖线也认，存一次就统一成半角逗号。

`ENABLED` **老台账没有这一列时所有账号都算启用**，第一次在页面上停用账号时会
自动补上。

`START_DATE` 是账号的启用日期，概览页从这一天累计消费到今天。**老台账没有这一列
也能读**，账号管理页那一列会显示「未设置」，第一次在页面上填日期时自动补列。
认这些写法：`2026-09-01`、`2026/09/01`、`2026.09.01`、`20260901`，以及 Excel 的
日期格式。**认不出来的值一律当成没填**——宁可显示「未设置」并提示去补，也不要拿
一个猜出来的日期去算整个账号的累计消费。

`START_DATE` 和 `ENABLED` 没有联动：停用再恢复不会改启用日期，它是业务上的合同
生效日，不是软删开关的时间戳。

`TG_CHAT_IDS` 一格里放这个账号的全部群组 ID，逗号隔开。手改时全角逗号、分号、换行
也都认，重复的只算一个；Excel 把单个 ID 自作主张存成了数字也没关系。页面上存一次就
统一成半角逗号。

但**上线之后请只从页面改**：本地另存一份再 scp 上去，会把页面上的改动整个覆盖掉。
两个入口同时用，迟早丢数据。

如果确实在服务器外改过台账（比如 scp 覆盖），页面上原来打开的那份就过期了——
这时点保存会看到「台账内容和页面上看到的对不上」并拒绝写入，刷新一下即可。
这是靠写入前核对「行号那一行的账号 ID 是否还是原来那个」实现的，宁可报错也不改错行。

单个账号查询失败（凭证错误、权限不足等）只会影响那一行，不影响其他账号。

### 查询失败时显示上一次查到的数

每次 CE 查询成功，都把这个账号的累计消费记进 `last-known-costs.json`（和台账在一起，
`.gitignore` 里；web 进程和日报任务是两个进程，所以存文件）。之后某天查询失败——凭证被
收了权限、被限流、网络断了——概览页和日报就拿上一次的数顶上：

- 金额照常显示，旁边标「截至 09-28」，下面一行写清这次失败的原因；
- 合计**算上**它（不然合计对不上表上的数），页脚写明「含 N 个账号上一次查到的数」；
- 从来没查成功过的账号，才照旧整行写「查询失败」、不进合计。

只在口径一样时才顶上：起算日、TAG 标签、计费口径都要和这次一致——改过启用日期或 TAG
之后，旧的数是另一个口径算的，拿来顶上反而误导。比率和额度照当前台账现乘。

额度阈值告警**不用**这个数：拿旧的数去判阈值只会晚报，CE 那段查不到就照旧跳过这一轮。

这个文件丢了、坏了都不要紧，最多是下次失败时没有旧数可顶，**不用备份**。

它只能记住「上线之后」查成功过的数：功能上线前就已经查不到的账号，要等权限恢复、查成功
一次之后才开始记。

## Telegram 告警

每个账号可以单独开 Telegram 告警，发到它自己的群——可以是**几个群**，一行一个，最多
10 个。在账号管理页的修改 / 新增弹窗里填群组 ID，再在表格的「TG 告警」列打开开关，
立刻生效（新增账号时填了群，开关直接就是开的）。一个开关管这个账号的全部消息，每条
都发给它的每一个群。每条消息都是一张深色卡片图，图片下面跟一段文字，见下面
《卡片长什么样》：

| 卡片 | 什么时候发 | 数据 |
|---|---|---|
| 📊 Bedrock 日报 | 每天 09:00（UTC+8） | CE 实账，自启用日期累计 |
| 🟢 用量开始 / 🔴 用量中断 | 状态切换时各一条 | CW 每小时调用次数；中断那张另带上一次调用的时间和那一小时的用量、预估费用 |
| ⚠️ 额度预警（50% / 80% / 90%），🚨 额度已用完 | 每档只发一次 | CE 实账 + CW 估算 |
| 🟢 新账号启用 / ⚫ 账号停用 / 🟢 账号恢复启用 | 在账号管理页新增、停用、恢复账号时 | 台账；停用那张另带 CE 实账 |
| 🟢 邮件告警已开启 / ⚫ 邮件告警已关闭 | 在账号管理页打开、关闭邮件告警时 | 台账（邮箱地址打码） |
| 🚨 / ⚠️ 邮件告警 | 告警邮箱收到 AWS 的要紧通知时 | 见《邮件告警》 |

开关**默认关**，老台账没有这两列一律算关——告警是往外发消息，必须主动开，和
`ENABLED` 的「空着算启用」刻意相反。停用的账号一条都不发（「账号停用」那张就是它的
最后一条）。

所有消息（包括测试消息）里账号都只写 12 位 ID，**不带上游**（台账的 `PARTNER` 列）。

部署（建 bot、拿群组 ID、两个 systemd timer）见 DEPLOY.md 第 7.3 节。

### 卡片长什么样

Telegram 的文字消息只有粗体、等宽、引用这几种格式，做不出颜色、边框、徽章、进度条和
大号数字，所以每条告警都画成一张深色卡片图（`cards.py`，用 Pillow 画），用 `sendPhoto`
发出去：

- **边框颜色跟着事情走**：日报、用量开始、新账号启用、账号恢复是绿框；额度 50% / 80%
  是橙框，90% 起和用量中断是红框；账号停用是灰框，测试消息是蓝框。
- **图片下面带一段文字**（caption）：账号 ID、账号邮箱和关键数字。通知预览、群内搜索、
  复制 UID 都靠它——图片里的字搜不到，也复制不了。
- **号码旁边写账号邮箱**（台账 `EMAIL` 列，完整地址）：卡片上 UID 后面一行灰字，日报表格里
  UID 下面一行小字。号码一眼认不出是谁，邮箱能。没填邮箱的账号就只有号码，卡片高度不变。
- **每张真的发出去的卡片记一行流水**（`ALERT_EVENTS_PATH`，见 `events.py`），运营看板的
  「最近告警」读它。dry-run 不记。
- **画不出来就退回发文字**：字体文件丢了、Pillow 出错时只发那段 caption，告警不会因为
  画图丢掉；同时记成问题，命令非零退出。
- **字体随包带着**（`src/bedrock_cost/fonts/`，都是 OFL 1.1 开源许可）：Noto Sans SC
  管中文、数字和英文，JetBrains Mono 管 UID。不用系统字体，本地和服务器画出来一模一样，
  服务器上什么字体都不用装。标题前的图标（柱状图、状态圆点、警告三角……）是代码画的，
  不依赖 emoji 字体。
- **尺寸**：出图 1200 px 宽，在 Telegram 普通画质的 1280 以内，不会被再压一遍。
- 每张卡片底部的署名来自 `TELEGRAM_CARD_SIGNATURE`（默认
  「This message was sent automatically by pokemoncloud」），在 `.env` 里写成空就不画这一行。

上线前想看看卡片长什么样：

```bash
bedrock-cost alerts daily --dry-run --save /tmp/cards
```

不发、不改告警状态，把要发的每一张卡片存成 PNG，拿下来看。

### 日报：和概览页同一组函数

调的就是概览页那一串：`cumulative_range` → `cost_explorer.fetch_all` →
`report.build_row`，**数字一分不差**。按群组 ID 拆开，每个群只看到自己的账号；几个
账号填同一个群 ID，就合成一张表；一个账号填了几个群，每个群的表里都有它。

表格四列：UID / 授信额度 / 累计消费 / 剩余额度。有问题的行这样标：

- **查询失败**：有上一次查到的数就照常显示、标橙，数字下面写「截至 09-28」（见上面
  《查询失败时显示上一次查到的数》）；从来没查成功过的才写「查询失败」、标红；
- **已超出额度**：剩余额度是红色的负数（写成 `-$1,234.56`）；
- **启用日期有问题**（没填、早于 CE 保留期）：数字照常，但余额可能偏高；
- 以上几种，UID 后面都有一个小圆点（红 = 查询失败 / 超额，橙 = 启用日期），原因逐条写
  在表格下面的「需要注意」里。

一个群超过 15 个账号就分成几张卡片发（「第 1/2 张」）：一张图放太多行，Telegram 一
压缩就看不清了。

### 用量切换：只在切换那一刻发

持续在用不刷屏，只有「无 → 有」和「有 → 无」时各发一条。「无用量」= 最近
`TELEGRAM_IDLE_HOURS` 个**完整**整点小时全是零调用（默认 1；MAP 流量常有突发空档，
嫌吵就调大）。

几条刻意的处理：

- **第一次运行只记基线、不发消息。** 刚开启告警时已经在用，发一条「开始有用量」是
  误导——其实早就在用了。
- **读不到 CloudWatch 时不判定。** 四个区里只要有一个查失败，这一轮就不做切换。缺一个
  区的零不能当成真的零，否则 CW 一限流就会误报「用量中断」。
- **有一个群收到就算发过了，全部失败才不落状态。** 全部失败（Telegram 连不上、Token
  失效）时状态保持原样，下一小时条件还成立会再发一次，而不是就此丢掉。只坏了一个群
  （bot 被踢了、ID 填错了）不能拖住状态，否则好好的那几个群每小时都会再收到一遍，
  直到有人修好那个 ID；坏掉的那个会报在运行结果里、以非零退出。额度阈值同一规则。
- **关掉告警会清掉这个账号的状态。** 以后再开启时从头建基线，不拿几周前的旧状态去比，
  免得一开启就收到一条过时的「用量中断」。

调用次数是**逐 ModelId 相加**的，不查不带维度的账号级 `Invocations`。后者只在写模型
用量页（现在的用量页签）时拿来对过一次账（318,978 = 318,978），生产代码从没依赖过它；而写这个功能时，
当初那几个有流量的账号凭证都已经失效了，没法重新验证它一定存在——`GetMetricData`
查一个**不存在**的指标也是返回空结果 + `StatusCode: Complete`，分不出「没用量」和
「指标不存在」。逐 ModelId 这条路用量页签天天在跑。

`ListMetrics` 只列近两周有数据的指标，但这里只看最近几个小时：上一小时有调用的模型
必然在两周内有数据、必然被列出来，所以对这个窗口没有缺口。

**「用量中断」那张卡片上还写着上一次调用的细节**（`cost_estimate.hour_usage`）：发的时候
再按分钟查一遍「上一次有调用的那一小时」——

- **上一次有调用**精确到分钟（Invocations 按分钟发点，这是 CloudWatch 能给的最细）；
- 那一小时的**调用次数**、输入 / 输出 token，有缓存读写时再列一行；
- **预估费用**：token × AWS 牌价，和预估成本页同一套定价，再按有无标签套台账的
  TAG / UNTAG 比率——和日报、额度告警一样是对外的金额。

有区读不到、或者有模型没单价时，卡片上会写「可能偏低」「按 0 算了」。按分钟的数据取不到
（比如 CloudWatch 限流）也照发中断告警，只是退回写「XX:00 那一小时」、不画用量那一块。
这一查只在发中断告警时才有：模型数 × 5 个指标 × 4 个区，每次不到一美分。

### 额度阈值：CE 实账 + CW 估算拼起来

```
累计消费 = CE 实账（启用日期 ~ 前天） + CW 估算（昨天 ~ 今天）
           两段都套 TAG_RATIO / UNTAG_RATIO，和概览页同口径
```

为什么不是单用一个：

- **光用 CE**：CE 有一到两天延迟，今天花的钱要后天才看得到，阈值告警会晚两天。
- **光用 CW**：`ListMetrics` 只列**近两周**有数据的模型。一个三周前用过、最近两周没再
  用的模型，根本不会被列出来——它那段 token 会从累计里悄悄消失，余额算高，阈值告警
  晚发或不发。

所以历史用 CE（完整），最近两天用 CW（及时，而且落在两周窗口里）。两段**按 UTC 日期**
切开、不重叠——CE 和 CW 的日桶都是 UTC 的，按本地日期切会让两段在凌晨重叠 8 小时。

CW 这段要套比率，所以得知道每一块钱是 TAG 还是 UNTAG：`cost_estimate.estimate_split`
逐 ModelId 定价（`build_estimate` 把配置归并进了底层模型，标签信息在归并时就丢了），
走带台账标签的推理配置算 TAG，直连原厂模型算 UNTAG。定价和预估成本页**同一套**——
同一个价目表、同一个计价档判定，有测试核对两边合计相等。

几条刻意的处理：

- **CE 那段每账号每天只查一次。** 结果存进状态文件，小时任务每小时都要这个数，不能每
  小时花一次 0.01 USD。缓存的 key 带着区间起止和 TAG 写法，任何一个变了才重查；比率
  是在读缓存时现乘的，改了比率立即生效。
- **一次跨过好几档只发最高那一档。** 比如刚开启告警时已经 85%，发一条「已用 80%」，
  不连着刷 50 / 80 两条。
- **额度或启用日期一改就重新计档。** 等于开了新的一期额度，已发的档位清零。
- **CE 或 CW 任何一段查失败，这一轮就不判。** 缺了一段只会低估，拿低估的数判阈值
  没意义。
- **没单价的模型会在告警里写明「按 0 算了」**，不悄悄少算。

**已知的差异**：CW 只看得到 Bedrock，CE 看得到账号里的全部服务。所以对最近两天有非
Bedrock 消费的账号，额度告警的累计会比日报少一点。实测 Jeff 那个账号：日报 $38.50，
小时任务 $37.17——差的 $1.33 就是最近两天 CE 已经记下、而 CW 看不到的那部分（这个
账号最近两周在四个美区一条 Bedrock 指标都没有）。两天后这部分会进 CE 那段，差异自动
消失。

### 状态文件

跨次运行要记住的东西放在 `alert-state.json`（和台账在一起，`.gitignore` 里）：上次有
没有用量、这一期已经发过哪些档位、CE 实账的缓存。临时文件 + 原子替换写入，写到一半
断电旧文件还是完整的；文件坏了就从头来——最坏的结果是重新建一次基线、把已达到的档位
再报一遍，比整个告警任务起不来强。**不用备份。**

### 为什么不塞进 web 进程

两个任务是由 systemd timer 调起的**独立短命进程**（`bedrock-cost alerts daily|hourly`），
跑完就退出：

- gunicorn 一重启，进程内的定时器就可能漏发或重发；
- 以后要是改成多 worker，每个 worker 都会跑一份，一条消息发 N 遍；
- timer 带 `Persistent=true`，服务器宕机回来会补跑一次。

有任何发送或取数失败都以非零退出，`systemctl --failed` 看得到。上线前用
`--dry-run` 看一眼要发什么——它不真的发，也不改告警状态；卡片照样会画一遍，画不出来
当场就报。加 `--save DIR` 还会把卡片存成 PNG。

### 账号变动通知：新增、停用、恢复

在账号管理页新增、停用、恢复一个账号，会当场给它的群发一张卡片：

- **新账号启用**：账号状态、授信额度、启用时间（点「添加账号」的那一刻）；
- **账号停用**：停用时间，外加停用前的累计消费和剩余额度——和概览页、日报同一组函数算
  （有缓存就用缓存，没有就查一次 CE，$0.01）；
- **账号恢复启用**：照「新账号启用」的样子，写恢复时间。
- **邮件告警已开启 / 已关闭**：在表格里点邮件告警开关时发，写监控状态、告警邮箱（打码成
  `r***@example.com`）和开关的时间；在修改弹窗里把告警邮箱清空（邮件告警跟着关）也发一张
  「已关闭」。

开着邮件告警的账号，新增、停用、恢复那三张卡片上会多一行「邮件告警：已开启 / 已停止 /
已恢复」，不另发一张。

**跟 TG 开关走**：开关开着、填了群才发；表格里只翻 TG 开关本身不发。停用的时候账号已经
不算「会收到告警」了，但这张「账号停用」正是它的最后一条消息，所以看的是开关和群，不看
账号启用没有。邮件告警的开关则要账号本身也启用着才发。删除账号不发卡片。

这类消息由 web 进程在请求里当场发，不走 systemd timer。**台账先写好**，通知发不出去
（没配 Token、群 ID 坏了、Telegram 连不上）只在页面上另起一条警告，改动照样生效，不回滚。

### Bot Token 只放 `.env`

`TELEGRAM_BOT_TOKEN` 在页面上看不到也改不了。能登录的人就能看到页面，Token 泄露等于
别人能冒充这个 bot 往你的群里发消息。Token 就在 Telegram API 的 URL 里
（`/bot<token>/sendMessage`），网络错误的文本很容易把整个 URL 原样带出来，所以往外抛
的错误信息都会先把 Token 擦掉。

### 「发测试消息」按钮

弹窗里填完群组 ID 可以点一下，立刻往填着的**每个群各发一张**测试卡片。结果贴在各自那
一行下面，失败的写明是 ID 错了、bot 不在群里还是没有发图片的权限（Telegram 的
`description` 翻译成人话），几个群里哪个坏了一眼看到；格式就不对的那行根本不发。卡片
画不出来、改发了文字时，那一行写「已发送（卡片画不出来，改发了文字……）」。按钮用 `formaction`
提交**同一个表单**，所以测的就是此刻填着的值，**不用先保存**；测完原样回填、重新打开同一
个弹窗，不丢输入。它**不写台账**。

### 不需要新的 AWS 权限

用到的 `ce:GetCostAndUsage`、`cloudwatch:ListMetrics` / `GetMetricData`、
`bedrock:ListInferenceProfiles` 概览和用量页签本来就要。

费用：日报每账号每天 1 次 CE（$0.01）；小时任务的 CE 部分每账号每天也只查 1 次（状态
文件缓存）。小时任务真正花钱的是 CloudWatch——`GetMetricData` 按请求的指标数计费，
$0.01 / 1,000 个。一个活跃账号每个区 15 个左右 ModelId，每小时要
「15 × 4 区（调用次数）+ 15 × 4 种 token × 4 区（估算）」≈ 300 个指标：

```
300 个/小时 × 24 × 30 ≈ 21.6 万个/月 × $0.01/千 ≈ $2.2/月 · 账号
```

没有 Bedrock 流量的账号（ListMetrics 列不出 ModelId）是 $0。

## 邮件告警

AWS 的封号、盗用、滥用这类通知只发到账号的 root 邮箱，常常几天都没人看到。每个账号可以
填一个**告警邮箱**，后台每 5 分钟收一次信，认出下面这几类就发一张 TG 卡片：

| 卡片 | 认的是 | 颜色 | 发到 |
|---|---|---|---|
| 模型权限被撤销 / 收到 AWS 滥用报告 | Trust & Safety 发的、主题含 Abuse Report | 红 | 账号的群 |
| 账号疑似被盗用 | 主题含 Suspicious activity in your AWS account、review your AWS Account and credentials | 红 | 账号的群 |
| 账号暂停 / 关闭 / 资源终止通知 | 主题含 suspended、closed、terminated | 红 | 账号的群 |
| AWS 开了工单 / 工单有新回复 | New Support case、RE:[CASE …] | 橙 | 账号的群 |
| root 账号安全变更 | MFA 被停用、Verify your identity、重置密码 | 橙 | 固定群 |

**其余一律不发**：Marketplace 的订阅和 offer 通知（开通模型时一来就是十几封）、其他 AWS
邮件、非 AWS 发来的邮件。发件人必须是 AWS 的域名；收件服务器验出 DMARC 不通过的当冒充，
也不发。

### 怎么开

修改（或新增）弹窗里的「告警邮箱」一栏填三样：

- **邮箱平台**：阿里邮箱（国际站的新加坡 / 香港 / 德国 / 美国，和中国站）、腾讯企业邮、
  QQ 邮箱、网易 163 / 126、网易企业邮、Gmail；别的选「其他平台」，自己填 IMAP 服务器
  （`imap.example.com:993`）。Outlook / Microsoft 365 不支持：它们已经关掉了密码登录
  IMAP，只能走 OAuth。
- **邮箱地址**：一般就是这个 AWS 账号的 root 邮箱。
- **密码**：**客户端密码，不是网页登录密码**——阿里邮箱是「三方客户端安全密码」，QQ / 163
  是授权码，Gmail 是应用专用密码。选了平台，输入框下面会提示这家要哪一种。

点「测试连接」会只读地登录一次，说收件箱里有几封、最近 50 封里有几封符合告警规则，
**不写台账**；填着的密码原地不动，测通了直接保存。

开关在表格的「邮件告警」列，和「TG 告警」一样：邮箱没填全开不了；新增时填了邮箱就是开的；
清空邮箱地址就关掉，存着的密码也一起删掉。开和关都会给这个账号的群发一张卡片（见
《账号变动通知》）。

阿里邮箱要先做两件事（在网页邮箱里，密码只显示一次）：管理员在管理后台开放「三方客户端
登录」和这个账号的 IMAP；然后「设置 → 账户与安全 → 账户安全 → 三方客户端安全密码 →
生成新密码」。这个密码可以单独删掉作废，不影响网页登录。

### 只读，只发新的

- 收件箱用 EXAMINE 打开、取信一律 `BODY.PEEK`，**不会把邮件标成已读**，也不动任何标记。
- 认类别只看信头（发件人 + 主题），认出来的那几封才取正文。
- **第一次收一个邮箱只记下「收到第几封了」，不补发旧邮件**，之后每次只看比上次新的。
  邮箱的编号体系变了（UIDVALIDITY）也当第一次；关掉邮件告警再打开，从打开那一刻算起。

### 卡片

和其他告警同一套样式：标题行（图标 + 标题 + 徽章）、详情面板（账号 UID、从邮件里取出的
字段、收到时间）、「邮件原文（节选）」（原主题 + 几段原文）、「怎么处理」、底部的发件人
和署名。

- **节选只留「发生了什么、要做什么、最后期限」**：称呼、客套、操作步骤、链接、机器翻译
  说明、页脚都去掉；已经写进字段的几行（Action、Case ID……）也不重复。
- **密钥只露头尾**（`AKIAEXAM…PLE1` 这样，和账号管理页一样），邮箱地址打码。
- **登录验证、重置密码这两种邮件，正文一个字都不取**：里面有验证码和重置链接。
- **只放 AWS 自己域名下的链接**（控制台的工单页之类）。申诉表单这种第三方链接只说
  「按邮件里的申诉方式」，不贴出去——假冒的「AWS 通知」不能借 bot 的嘴让人去点链接。
- 图片下面的文字：标题、字段、原主题、节选（引用块）和工单链接，放不下就只截节选。

### 发到哪

- 邮件里写了台账里的账号 ID → 这个账号的 TG 群（跟 TG 开关走）；
- 没写账号 ID → 收到这封邮件的那个账号的群；
- 写的账号不在台账里，或者那个账号的 TG 告警没开 → 固定群（`.env` 的 `MAIL_ALERT_CHAT_IDS`）；
- root 安全类 → 先发固定群，没配固定群才发账号的群：root 是运维管的，不是用账号的人。

两边都没有就记成问题、跳过这封。几个账号填了同一个邮箱只收一次，认不出是谁的就发固定群。

### 去重和重试

- 同一个账号、同一类、同一个主题，`MAIL_DEDUPE_MINUTES`（默认 60）分钟内只发一次：AWS 常把
  同一条通知从 `no-reply@amazonaws.com` 和 `health@aws.com` 各发一遍。
- 一封邮件的所有群都发失败（Telegram 连不上、Token 失效）就停在这封，下一轮重试；连续 6 轮
  （约半小时）都失败就跳过它、记成问题，不让它卡住后面的邮件。
- 一轮最多发 20 张卡片，剩下的下一轮接着发。

### 邮箱密码只进不出

存在台账的 `MAIL_PASSWORD` 列，和 SK 一样是明文，同样只进不出：页面上不回显（修改时留空 =
不改）、校验失败回填表单时不回填、审计日志里只记「已更新」、`Account` 的 `repr` 屏蔽、登录
报错里擦掉。换了邮箱地址必须重填密码。

### 状态文件和预览

收信进度和去重记录在 `mail-state.json`（和台账在一起，`.gitignore` 里）。丢了不要紧：最坏是
每个邮箱重新建一次基线，漏掉这几分钟里到的邮件。**不用备份。**

想先看看规则在真实邮箱上认出什么、卡片长什么样：

```bash
bedrock-cost mail check --dry-run --recent 30 --save /tmp/mail-cards
```

不看收信进度、不发、不改状态，把最近 30 封按规则过一遍，要发的卡片存成 PNG。部署（systemd
timer）见 DEPLOY.md 第 7.4 节。

## 安全须知

- `cred.xlsx` 里的 AK/SK 是明文。这些密钥只在内存中传给 boto3，**不会**出现在页面、日志或错误信息里（`Account` 的 `repr` 屏蔽了这两个字段，CE 报错文本也会做脱敏）。告警邮箱的密码（`MAIL_PASSWORD`）同样是明文、同样只进不出，只交给 IMAP 登录用。
- `.env`、`cred.xlsx`、`ledger-backups/`、`ledger-audit.log` 都在 `.gitignore` 里，不要提交或分享。
- 账号管理页的写操作带 CSRF 令牌。会话 cookie 本来就是 `SameSite=Lax`（浏览器不会把它带上跨站 POST），令牌是第二道。
- **登录即可改台账**：目前是单口令，没有区分「只读」和「管理员」。谁能登录，谁就能改额度、停用账号。要区分角色需要换成真正的用户体系。
- 给这些 AK/SK 配最小权限即可，见开头的《AK/SK 需要什么权限》。
- 默认只监听 `127.0.0.1`。要对外提供访问，请用 gunicorn/waitress + Nginx 并启用 HTTPS，同时把 `SESSION_COOKIE_SECURE` 打开——当前的登录机制（单账号 + 内存级失败锁定）是按本地自用设计的。

三种东西，三个地方：

| 是什么 | 放在哪 | 样子 |
|---|---|---|
| 报错（查询失败、读不到某个区） | 右上角的弹窗 | 红色，一直留着直到点 × 关掉 |

里的模板克隆，文字一律 `textContent`。

「刷新数据」都在内容区的工具条里。

## 等待动效

全站是服务端同步渲染：点链接或改筛选之后，浏览器会一直显示**旧页面**直到新页面
回来。所以「加载中」就盖在旧页面上——内容区压暗（`opacity: .5`，不闪骨架屏、不跳
布局），中央浮一个像素小生物加一行文案。

素材是 `static/loading.webm`，**带 alpha 通道**（实测采样 96% 全透明，边缘有半透明
抗锯齿），所以直接铺上去就行，不需要混合模式也不需要卡片托底。刻意**不加**
`mix-blend-mode: darken` 之类：小生物身上有比纸色更亮的高光（`rgb(248,216,200)`），
darken 会把它压掉。

文件名不写死：`filters.loading_media()` 按 `loading.webm` → `loading.mp4` 的顺序挑
第一个存在的（带 alpha 的只能是 webm，mp4 的 alpha 只有 Safari 认），两个都没有就
不渲染 `<video>`，只剩文案。换素材刷新页面即生效，不用重启。

几个刻意的选择：

- **动效放在 `.content` 外面。** `.content.is-loading` 是整块 `opacity`，动效放在
  里面会被一起压暗。
- **压暗立刻生效，动效延后 250 毫秒。** 命中缓存时响应只要几十毫秒，闪一下小生物
  比根本不显示更难受。
- **文案说的是「目标页在等什么」。** 点导航时当前页还不知道要去哪，所以文案挂在
  链接的 `data-loading` / `data-loading-note` 上，由 `shell.html` 里的
  `LOADING_HINTS` 按导航 key 查表带出去；筛选提交后还留在同一页，用的是本页自己
  通过 `{% block loading_label %}` 声明的那条。配额页写的是「正在拉四个区的配额 ·
  首次约 45 秒」——45 秒的等待里，让人知道在等什么。
- **点数用纯 CSS。** `文案.` → `文案..` → `文案...`：第一个点常亮，后两个各挂一条
  1.2 秒的动画，每段的两个关键帧取同值，所以是硬切而不是渐变。
- **不拦点击**（`pointer-events: none`）：等着的时候还想点别处就让他点。也因此显隐
  用的是 `visibility` 而不是 `opacity`——`opacity < 1` 会让这一层变成隔离组。
- **`prefers-reduced-motion: reduce` 时撤掉视频**，点数固定成三个。
- 脚本只有一份，在 `shell.html` 里。原先四个页面各自复制了一遍「改动即提交 + 压暗」，
  已经收拢：表单靠 `form.filters-auto` 这个类被统一接管，所以**类丢了表单就变哑巴**
  （有测试守着）。

| `--accent` | `#d97757` | 陶土色：填充、图形、选中态 |
| `--accent-dim` | `#a94f2e` | 陶土色当文字（链接） |
| `--ok` / `--warn` / `--danger` / `--info` | `#2c7652` / `#8c610f` / `#bc3b2e` / `#2f6aa8` | 状态色，只用在状态上 |

**每个当文字用的令牌都过了 WCAG 4.5:1**（白卡片、象牙底、燕麦底三种底色上都算过），只做
填充和描边的按图形元素的 3:1 收。改色请重新算，别只看着顺眼。

**主按钮是墨黑不是陶土**：白字放在陶土色上只有 3.1:1，不达标；放在墨黑上是 18:1。
陶土色留给选中态、焦点环、进度这些小面积的地方，链接用压暗一档的那个。

### 字体

`base.html` 里从 Google Fonts 引 Inter、Source Serif 4 和 Noto Serif SC（只要 500 一个字重），
带 `display=swap`：

- 界面和数字都走无衬线（Inter → 苹方 / 雅黑）。大数字和正文同一套无衬线，衬线大数字读起来
  像装饰；表格里的数字列用 `tabular-nums` 对齐。
- 标题用衬线：西文落在 Source Serif 4，中文落在思源宋体（Noto Serif SC），和 claude.com 的
  衬线标题一个气质。Google Fonts 连不上时（比如在中国大陆）中文退到雅黑 / 苹方——宋体在大
  字号下很难看，所以栈里刻意不放 SimSun。

> **在中国大陆访问不到 Google Fonts。** 那时 `swap` 会让页面立刻用系统字体渲染，
> 不白屏也不卡等待，只是字体退回系统的——版式和配色不受影响。要彻底解决就把字体
> 文件自托管到 `static/`。

### 图表

全部是服务端画的 SVG（`chart.py`），没有前端图表库。交互（悬浮提示、图例点选、气泡拖动）
在 `static/app.js`，动画都包在 `prefers-reduced-motion: no-preference` 里，系统开了「减弱动画」
就不动。

| 图 | 函数 | 用在 |
|---|---|---|
| 堆叠面积图 | `render_stacked_areas` | 成本、预估页签 |
| 折线图 | `render_lines` / `render_views` | 用量页签的主图、摘要的近 7 天调用、客户页的近 24 小时调用（线尾是账号头像） |
| 堆叠柱状图 | `render_bars` | 概览和摘要的近 30 天成本、客户页的每天消费、运营看板的近 12 个月 |
| 还能用几天 | `render_runway` | 客户页 |
| 半圆仪表 | `render_gauge` | 额度使用 |
| 气泡 | `render_bubbles` | 消费构成、模型占比 |
| 迷你柱 | `render_spark` | 卡片和指标卡里 |
| 热力格、一周作息 | `heat_style`、`week_grid` | 用量页签 |

几条共同的规矩：网格线一律是比底色深一档的发丝实线，零线再深一档（虚线读起来像「预测」
或「阈值」，不用）；两个及以上序列才有图例；字一律用文本色，不用序列色；只在最高的那个点上
做一处直接标注，其余交给坐标轴、悬浮提示和明细表。

### 图表：放大、拖动

带时间轴的图（堆叠柱状图、折线图、堆叠面积图、客户页的「还能用几天」）都能**沿横轴放大、左右拖**：

- 放大缩小：鼠标划到图上**滚滚轮**，往上放大、往下缩小，以鼠标所在的位置为中心（触控板捏合也一样）；
  手机上双指捏合。缩到全貌还往下滚、放到最大还往上滚，就不拦着，照常滚页面，不会卡在图上。
- 放大以后：按住拖、横着滑触控板、或者 Shift + 滚轮，左右看；双击图回到全貌。没有按钮。
- 只拉横轴：纵轴和字的大小不变，柱子变宽、线拉长，横轴的字跟着挪，放得下就多显示几格（服务端把每一格
  的字都画了，平时隔几格才显示一个）。重新算的是每个图形的横坐标，不是把整张图拉伸，所以线不会变粗、
  圆点不会变扁；悬浮提示、图例点选照常用。最多放大到能看清四五格（最多 24 倍）。

服务端在 `<svg>` 上写 `data-zoom="左,右"`（绘图区的横向范围）、`data-zoom-n`（几格）、
`data-zoom-band`（一格多宽）、`data-zoom-gap`（字之间至少隔多宽，0 = 刻度是挑好的、只挪不加），
见 `chart._zoom_attrs`。仪表、气泡、迷你柱没有时间轴，不放大。折线图线尾的头像放大时藏起来（标的是全貌里的末值）。

### 图表：堆叠面积图

趋势图是**堆叠面积图**（`chart.render_stacked_areas`），成本页签和预估页签共用。
左侧 Y 轴，网格是实线发丝。

每条序列是**上沿一条实色线 + 下方同色半透明填充**（`AREA_FILL_OPACITY = 0.28`）。
分工是刻意的：

- **线负责识别**，用的就是 `SERIES_COLORS` 里那个值——也就是下面那套校验确认过
  ≥3:1 的颜色。所以校验结论对「真正承载信息的元素」依然成立。
- **面积只负责体量感**，是装饰，淡一点更好读。

反过来做（面积实色、没有线）在稀疏数据上很难看：本项目的日用量大部分天是 0，
只有零星几天有量，实色填充会把这些孤立的峰画成几块沉重的三角形。

堆叠的各条带在几何上互不重叠（一条压在另一条**之上**，不是叠在一起），所以半透明
只是各自对着纸底变淡，不会互相透叠成一团脏色。

用量页签的折线图是同样的风格，但填充用的是**渐变**而不是平涂：折线是**互相重叠**的，每条
的填充都从自己那条线一直铺到零线，平涂的话底部会层层叠加成一团脏色。所以用「紧贴线最浓、
往零线渐隐到全透明」的渐变（`AREA_TOP_OPACITY = 0.16`），重叠发生在各自已经很淡的区域。
渐变的 id 带上视图名——五个视图在同一个页面上，SVG 的 id 是全文档共享的。

### 图表色板

色相沿用改主题之前那一套，只把黄和紫压暗到浅底上够 3:1。**不换色相是有意的**：
`assign_slots` 按名字哈希分配色槽，换了色相等于所有人记住的「哪个模型是什么颜色」
全部作废，而这次要解决的只是底色变浅带来的对比度问题。

改色或换底色都要重跑校验（Windows 的控制台要先设 `PYTHONIOENCODING=utf-8`，不然中文输出报编码错）：

```bash
python scripts/validate_palette.py
```

四项检查：对比度、亮度带（分类色板要平，有梯度会读出并不存在的大小顺序）、色度下限、
色觉障碍分离度（红/绿/蓝三种模拟下的 ΔE2000）。

最后一项只防退化、不设达标线——这套色相本来就没为色觉障碍优化过（红色盲下蓝与紫
只差 ΔE 1.8）。改主题时它立刻发挥了作用：紫色单纯压暗会让这个数掉到 0.7，脚本拦下来了，
改成「压暗 + 色相往洋红挪 3°」之后反而升到 2.0。

几条约定：

- **应用工厂**：没有模块级的全局 `app`，一律 `create_app()`。测试可以按需造带
  不同配置的实例，也不会在 import 时就产生副作用。
- **蓝图**：`auth`（登录）、`main`（概览）、`ops`（运营看板）、`account`（账号页）、
  `accounts`（账号管理）五个，所以模板里的 endpoint 是 `main.index`、`account.usage`、
  `accounts.index` 这种带前缀的写法。
- **只有一处写台账**：`excel_source` 的 `create_account` / `update_account` /
  `set_enabled` / `delete_account` 和两个开关，它们共用同一条「加锁 → 校验 → 备份 →
  原子替换 → 清缓存 → 审计」的流水线（备份只有新增和修改才做）。视图层只做表单进出，
  不直接碰 openpyxl。
- **默认口径不含停用账号**：`load_accounts()` 只返回启用中的，账号管理页显式传
  `include_disabled=True`。新增查询页时不用记得过滤，默认就是对的。
- **日期逻辑不碰 request**：`resolve_range(args, today)` 收一个普通映射，视图
  里传 `request.args`，测试里传字典，不用假造请求上下文。
- **图表色板只有一处定义**：都在 `chart.py`，模板里图例和表格的色块通过 Jinja
  全局 `series_color()` 取同一套值，CSS 里不重复维护。有个测试专门断言页面上
  出现的颜色都在色板内。
- **跨模块共用的函数不带下划线**：`cost_explorer.build_filter` 等是给
  `usage_explorer` 用的，所以是公开名。

## 测试

```bash
pytest
```

一千多个用例，两分钟左右跑完，**不联网、不花钱**：Cost Explorer 调用被替换成 fake，
台账指向临时 xlsx，登录口令也换成固定值（不依赖你机器上的 `.env`）。Telegram 和邮箱
服务器都连不上——哪个用例忘了替换，会直接失败而不是真的发出去 / 登录上去。AWS 也一样：
`conftest.py` 在 botocore 真正发 HTTP 的那一步拦下来，忘了 fake 的用例立刻失败，而不是带着
假凭证去连真端点、再退避重试半天（以前漏了三条，整套测试被拖到四十多分钟）。

邮件告警的用例（`tests/test_mail.py`、`tests/test_accounts_mail.py`）用一个假的 IMAP 服务器，
它对「只读」较真：取信没用 `BODY.PEEK`、打开收件箱没用只读模式都直接判失败。样例邮件在
`tests/mail_samples.py`，结构照真实的 AWS 通知，账号、密钥、工单号都是假的。

账号管理页的用例（`tests/test_accounts.py`）重点不在「功能能用」，而在「写坏了
会怎样」：编辑路径上 AK/SK 一个字节都不能变、校验没过时文件的 mtime 都不许动、
软删之后其他账号的 `key` 不许位移、行号对不上时宁可报错也不改错行。

概览页和下钻页的 fake 都从同两个常量算消费，所以「下钻任一维度加总 == 概览总
消费」这条不变量测出来才有意义，不会因为两边各造一套数字而虚假通过。

预估成本的用例（`tests/test_cost_estimate.py`）盯的是「数出来了但是错的」那一类：
四个计数器不能相减、直连和推理配置的同一个模型要并成一行、计价档选错就是 10% 的
偏差、没在价目表里的模型不能按 0 悄悄算进总额。

另有一组打 AWS 真实价目表的用例（`tests/test_pricing_live.py`），也标了 `integration`，
但**不需要凭证也不花钱**——价目表端点是公开的。它当哨兵用：AWS 哪天改了 service code、
改了 usagetype 写法、或者现役模型缺了单价，这几条会先炸，而不是等页面上悄悄少算钱。

```bash
pytest -m integration tests/test_pricing_live.py
```

真实调用 CE 的用例在 `tests/test_integration.py`，标了 `integration`，默认跳过：

```bash
pytest -m integration
```

跑它需要项目根有真实的 `cred.xlsx`。**注意 CE 按请求计费**（约 0.01 USD/次），
一轮下来是 账号数 × 用例数 次请求。它验证的是 fake 测不到的东西：标签拆分与
账号总额精确相等、按月查询在区间从月中开始时不错桶、缓存真的省掉一次请求、
无效凭证的报错不含密钥原文。
